Как устроен Resheto

В проекте есть один основной сценарий, вокруг которого распределены файлы: получить задание → загрузить правила → прочитать проверяемые файлы → найти совпадения → сохранить и показать результат.

В model.h находятся основные данные, которыми обмениваются части программы. Их стоит понять раньше алгоритмов:
Тип	Что означает	Пример
Request	Что нужно проверить и с какими параметрами	Проверить report.bin, взять указанную базу, сохранить историю по указанному пути
Signature	Одно правило обнаружения	SHA-256 известного файла либо искомая последовательность байтов
Snapshot	Загруженный в память набор правил для задания	Версия базы, список Signature и подготовленный поисковый индекс
Result	Результат проверки одного объекта	Файл проверен, найдено такое-то правило на таком-то смещении
Job	Состояние и сводка всего задания	Проверено 150 файлов, совпадений 2, ошибок 1

Связь между ними такая:

    Request задаёт работу. Snapshot содержит правила. Для каждого файла получается Result. Все результаты учитываются в одном Job.

Если проверяется один файл, обычно будет один Result. Если каталог с сотней файлов — результатов будет много, а задание Job по-прежнему одно.
Как проходит проверка

Теперь проследим выполнение.
1. gui.cpp открывает приложение, mainwindow.cpp принимает твои действия.

gui.cpp содержит main() — точку входа в графическую программу. Она создаёт приложение Qt, получает начальные параметры, создаёт окно MainWindow и запускает обработку событий: нажатий, перерисовки и прочего.

Основная работа окна находится в mainwindow.cpp.

При нажатии «Проверить» вызывается MainWindow::start(). Эта функция собирает Request из полей окна:
path          → какой файл или каталог проверить
signaturePath → откуда взять правила
storagePath   → куда сохранить результаты
recursive     → заходить ли в подкаталоги
cancel        → общий признак запроса отмены

После этого окно вызывает:
controller_.submit(r);

То есть передаёт подготовленное задание контроллеру.
2. controller.cpp передаёт работу фоновому потоку.

В controller.cpp реализован класс Controller.

У него четыре основных действия:

    submit() — принять задание;
    loop() — дождаться задания и выполнить его в рабочем потоке;
    cancel() — выставить признак отмены;
    progress() — вернуть текущую сводку.

Внутри loop() находится важный вызов:
runJob(std::move(request), ...);

Здесь начинается само сканирование.

Второй аргумент — функция, которой runJob() периодически передаёт обновлённый Job. Контроллер сохраняет эту сводку, а окно затем получает её через progress().

Поэтому окно продолжает реагировать на нажатия во время проверки.
3. scanner.cpp: runJob() организует всё задание.

В scanner.cpp есть две основные функции с разным масштабом ответственности:
runJob()   — выполнить задание целиком
scanFile() — проверить один файл

runJob():

    Создаёт Job: идентификатор, время начала, исходный путь.
    Открывает хранилище результатов через Store.
    Загружает правила через loadSignatures().
    Определяет, что выбрано: файл или каталог.
    Для каждого обычного файла вызывает scanFile().
    Сохраняет результаты и обновляет счётчики.
    Записывает завершение задания.

Если выбран каталог, обход тоже находится здесь. runJob() решает, в какой подкаталог войти, что пропустить и какую ошибку записать.

Таким образом, runJob() связывает остальные компоненты в рабочую последовательность.
4. signatures.cpp превращает базу на диске в Snapshot.

В signatures.cpp функция loadSignatures() получает путь к базе.

Она проверяет контрольную сумму, структуру SQLite и содержимое правил. Затем создаёт:
Snapshot
├── версия и источник базы
├── entries: список Signature
└── index: SearchIndex для быстрого поиска

Одна Signature содержит:

    id, name, version — идентификатор, название и версия правила;
    kind — HASH или PATTERN;
    value — хеш либо искомые байты;
    mask — какие байты шаблона нужно сравнивать;
    offset — обязательная позиция, если задана;
    minSize, maxSize — ограничения размера проверяемого файла.

Например, условное контрольное правило может означать:

    Найти байты ABC, затем любой один байт, затем DEF.

В value лежат байты шаблона, а mask указывает: этот байт сравниваем, этот игнорируем.

После загрузки задание пользуется своим Snapshot. Замена выбранной версии базы во время проверки не меняет правила посреди этого задания.
5. scanFile() читает файл через file_access.cpp.

Вернёмся в scanFile().

Она создаёт объект:
ReadFile file(path);

Класс ReadFile реализован в file_access.cpp. Он предоставляет понятные операции:

    read() — прочитать очередной блок;
    size() — узнать исходный размер;
    identity() — получить идентичность открытого объекта;
    unchanged() — проверить, сохранился ли исходный объект без обнаруженных изменений.

Внутри находятся различия Windows и Linux: системные способы открытия и чтения файлов. Остальной анализатор обращается к одному интерфейсу ReadFile.

Дальше scanFile() читает файл блоками, по умолчанию по 64 КиБ. Каждый блок используется для двух действий:
прочитанные байты
    ├── добавляются в расчёт SHA-256
    └── передаются в поиск PATTERN

Между блоками сохраняется хвост предыдущих данных, чтобы шаблон, начавшийся в одном блоке и закончившийся в следующем, тоже обнаруживался.
6. search.cpp отвечает за поиск среди загруженных правил.

В search.cpp реализован класс SearchIndex.

Он создаётся при загрузке базы и подготавливает правила для многократного использования.

У него два основных метода:

    patterns() — поиск байтовых шаблонов в очередном окне данных;
    digest() — поиск готового SHA-256 среди HASH-правил.

Для HASH используется таблица быстрого поиска: вычисленный хеш позволяет перейти к подходящим записям базы.

Для PATTERN строится общий поисковый автомат. Он ищет характерные участки сразу нескольких шаблонов, а для найденных кандидатов проверяет весь шаблон, маску и ограничения. Правила с фиксированным смещением проверяются в указанной позиции.

Распределение ответственности здесь такое:

    scanFile() управляет чтением и порядком проверки. SearchIndex сопоставляет полученные данные с правилами.

После полного чтения scanFile() проверяет, что файл не изменился. Затем формирует итог:

    найден PATTERN — записывает выбранный шаблон и смещение;
    PATTERN не найден — ищет окончательный SHA-256 через digest();
    совпадений нет — no_match;
    чтение сорвалось или проверка отменена — not_checked с причиной.

Сейчас сохраняется одно выбранное обнаружение на файл. Даже после найденного PATTERN чтение продолжается: поздняя ошибка не должна превратиться в успешную проверку.

При чтении исходника обрати внимание: в начале scanner.cpp есть отдельная функция findPattern(). Основной маршрут сканирования сейчас использует SearchIndex::patterns(); findPattern() также отдельно проверяется тестами.
7. database.cpp сохраняет результат, а окно читает его для показа.

scanFile() возвращает Result в runJob(). Затем runJob() обновляет счётчики Job и вызывает Store::append().

В database.cpp находятся два уровня:

    Database — открытие SQLite, выполнение SQL и управление транзакциями;
    Store — операции предметной области: начать задание, добавить результат, завершить, прочитать историю.

Основные вызовы:
Store::start()  → записать начало Job
Store::append() → записать Result и обновлённую сводку
Store::finish() → записать завершение Job
Store::query()  → получить результаты для экрана

При обнаружении дополнительно создаётся запись в таблице detections. В events записываются события задания.

Здесь важно различать две базы:
Файл базы	Содержание
signatures.db	Правила, по которым проверяют
resheto.db	Что проверяли и что получилось

Окно получает краткие счётчики от контроллера, а строки таблицы читает через Store::query(). В запросе передаются ResultQuery — фильтр, поиск, сортировка и страница. Обратно приходит ResultPage — найденные строки и их общее количество.

Поэтому фильтр «Совпадения» ищет по всему заданию, даже если обнаружение находится далеко за первой страницей.

Остальные файлы теперь можно привязать к этому сценарию:

    model.cpp переводит Result и Job в JSON и обратно, строго проверяет прочитанные данные, формирует подписи состояний и код завершения.
    import.cpp готовит новые версии рабочей базы. importSnapshot() импортирует внешний снимок, activateVersion() выбирает готовую версию, resolveSignaturePath() находит базу по указателю current.json.
    api.h объединяет публичные заголовки для подключения модуля другой программой.
    cli.cpp собирает Request из аргументов терминала и запускает тот же контроллер и анализатор.
    import_main.cpp предоставляет команды для импорта и выбора версий; prepare.cpp — для подготовки баз и безопасных контрольных данных.
    benchmark.cpp запускает измерения производительности.
    CMakeLists.txt задаёт, как из этих исходников собрать общую библиотеку, GUI, консольные инструменты и тесты.

Для первого чтения я бы выбрал такой маршрут:

    model.h — понять пять основных типов данных.
    MainWindow::start() — увидеть, как из полей окна получается Request.
    Controller::loop() — найти переход к фоновой работе.
    runJob() — проследить последовательность задания.
    scanFile() — понять проверку одного файла.
    После этого — loadSignatures(), SearchIndex и Store, когда уже понятно, зачем их вызывают.

При каждом переходе достаточно задавать три вопроса: что функция получила, что сделала и что передала дальше. В этом проекте ответы в основном укладываются в цепочку Request → Snapshot → Result → Job.

1. src — исходный код программы

Здесь лежат исходники C++. Когда мы исправляем поведение сканера или добавляем возможность в окно, обычно меняем этот каталог.

Внутри две основные части.

core — вся содержательная работа:

    представление задания, правил и результатов;
    загрузка базы;
    чтение файлов;
    поиск HASH и PATTERN;
    обход каталогов;
    фоновое выполнение;
    сохранение истории;
    импорт новых версий правил.

Эта часть собирается в общую библиотеку Resheto::Core. Ею пользуются окно, консольная программа, тесты и внешний пример.

gui — общение с пользователем: поля, кнопки, таблица, фильтры, сообщения. Окно собирает запрос, передаёт ядру и показывает полученные сведения.

Непосредственно в src находятся точки входа отдельных программ: GUI, CLI, импортёр, подготовка контрольных данных и измеритель производительности.

Связь такая:

В core написано, как проверить файл. В gui — как дать пользователю запустить эту проверку и увидеть результат.
2. data — контрольные исходные данные

Сейчас здесь находится demo_signatures.json с небольшим набором контрольных правил.

Он нужен, чтобы заранее знать ожидаемый ответ. Например:

Создадим безопасный файл с определёнными байтами. Контрольное правило должно их найти.

Средство подготовки читает этот JSON и создаёт:

    контрольную SQLite-базу;
    безопасные файлы с совпадениями;
    файлы без совпадений.

Созданные файлы попадают в выбранный выходной каталог, например в control.

То есть data содержит исходный рецепт для проверки работы алгоритма, а подготовленные примеры появляются отдельно.
3. distribution — рабочие правила

Здесь находится рабочая база известных угроз.

В source сохранены исходные материалы внешнего источника:

    полученный список SHA-256;
    лицензия;
    описание источника;
    сведения о версии, дате получения и контрольной сумме.

Это позволяет ответить: «Откуда взялись записи и из каких данных можно повторить импорт?»

В working находится подготовленная поставка, которую умеет загрузить сканер.

Важны два элемента:

    current.json — указатель на выбранную версию;
    versions — каталоги отдельных версий.

В каталоге каждой версии лежат:

Файл    Назначение

signatures.db   Готовые правила SQLite

signatures.db.sha256    Контрольная сумма базы

manifest.json   Сведения об источнике, версии и количестве записей

source.txt  Исходные данные этой версии

Длинное название каталога версии — её уникальный идентификатор.

При подготовке обновления создаётся новый каталог версии. После проверки переключается current.json. Так сохраняется предыдущая поставка.

Связь двух частей:

source — из чего готовили. working — что получилось и какую версию сейчас выбрали.

Текущая рабочая поставка содержит HASH. Контрольные PATTERN находятся в отдельном наборе.
4. tests — автоматические проверки

Здесь описаны автоматические сценарии с ожидаемыми результатами.

Например, тест:

    Создаёт временный файл.
    Записывает известные байты.
    Готовит правило.
    Вызывает настоящее ядро.
    Проверяет, что совпадение найдено на ожидаемой позиции.

Основные группы:

    core_tests.cpp — чтение, поиск, маски, границы блоков, обход, отмена, ошибки;
    audit_tests.cpp — строгая проверка сохранённых данных и граничных случаев;
    completion_tests.cpp — индексированный поиск, происхождение рабочей базы, импорт и глобальные запросы результатов;
    integration.cpp — запуск консольных инструментов целиком;
    gui_tests.cpp — поведение окна;
    powershell_scripts.ps1 — работа сценариев запуска.

Обычно данные теста создаются во временном каталоге. Сами файлы в tests содержат инструкции проверки, а создаваемые ими файлы существуют отдельно.
5. scripts — сценарии запуска

Эти сценарии позволяют запускать несколько действий одной командой.

Например, start.ps1 -Control подготавливает контрольные данные при необходимости и открывает окно с нужными путями.

Сейчас здесь:

    start.ps1 — обычный запуск GUI или запуск с контрольными данными;
    demo.ps1 — последовательный показ сканирования, ошибок, отмены и чтения истории;
    demo-results.ps1 — подготовка большого задания для проверки поиска обнаружения;
    fetch-signatures.ps1 — отдельное получение внешних метаданных и запуск импорта;
    measure.ps1 — прогоны измерений;
    common.ps1 — общие функции остальных сценариев: поиск инструментов, передача аргументов, запуск и запись вывода.

Связь с исходниками:

В src реализованы инструменты. Сценарии из scripts запускают собранные инструменты в нужном порядке.
6. consumer — пример подключения ядра

Это небольшой самостоятельный CMake-проект.

Он подключает Resheto::Core и вызывает её C++-интерфейс. Через него видно, как будущая служба или другая оболочка сможет воспользоваться сканером.

Разница с тестами в назначении: здесь показано именно подключение библиотеки из отдельного проекта.

Можно представить, что разработчик другой программы говорит:

«Мне нужен ваш поиск файловых угроз. Подключаю библиотеку, передаю Request, получаю Job и читаю результаты».
7. docs — документация

Документы отвечают на разные вопросы:

    implementation.md — как устроена реализация;
    integration.md — как подключить библиотеку;
    signature_sources.md — откуда правила и как обновлять поставку;
    verification.md — какие проверки выполнялись и с каким результатом;
    performance.md — ограничения и измерения производительности;
    lab3_demo.md — как повторить показ;
    eicar_manual.md — отдельная инструкция ручной проверки EICAR.

measurements содержит сохранённые численные результаты измерений: время, память, параметры среды. Документ о производительности объясняет эти данные.

archive хранит архивный документ предыдущего этапа.

При запуске сканера эти документы не читаются. Они нужны человеку, который разбирается, проверяет или продолжает проект.
8. build — результаты сборки и запусков

Здесь смешаны несколько видов создаваемых файлов.

В build/windows CMake и Visual Studio хранят настройки сборки, промежуточные файлы, отчёты тестов и готовые приложения.

Вложенные каталоги имеют техническое назначение:

    CMakeFiles, .qt — служебные данные средств сборки;
    каталоги с окончанием _autogen — автоматически созданный код для Qt;
    каталоги .dir и x64 — промежуточные результаты компиляции;
    Testing — данные запусков CTest;
    Release — собранные .exe и библиотеки.

В manual находятся данные ручных запусков:

    results.db — история при запуске через стандартный сценарий;
    другие базы с результатами отдельных проверок;
    control — подготовленная контрольная база;
    fixtures — безопасные файлы для неё.

Здесь особенно полезно помнить:

В src написан сканер. В Release лежит собранный сканер. В manual сохраняются данные его ручных запусков.
9. .tools — локальные инструменты разработки

В локальном Qt SDK находится локальный Qt SDK версии 6.8.3.

Внутри SDK:

    include — заголовки Qt для компиляции;
    lib — библиотеки для подключения;
    bin — инструменты и DLL;
    plugins — подключаемые компоненты Qt, в том числе драйверы;
    остальные папки — документация и сведения для сборки.

В вспомогательной Python-среде находятся вспомогательные Python-пакеты, включая средства установки Qt и инструменты сборки.

Сам сканер написан на C++; содержимое этого каталога относится к подготовке среды разработки.
10. .git — история проекта

Git хранит здесь версии файлов, ветки и сведения об изменениях.

Внутренние objects, refs, logs и другие папки обслуживает сам Git. Они позволяют посмотреть предыдущую версию кода, сравнить изменения и восстановить нужное состояние.

Теперь эти каталоги можно связать на одном обычном запуске:

    Разработчик меняет код в src.
    CMake собирает его с использованием Qt из .tools.
    Приложение появляется в Release.
    Ты запускаешь его через start.ps1.
    Программа загружает рабочие правила из working.
    Проверяет выбранный тобой файл.
    Сохраняет историю в manual/results.db — это путь по умолчанию именно у сценария запуска.
