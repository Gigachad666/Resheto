# Как сейчас устроено Решето

Этот текст объясняет готовую программу после этапов 3 и 4: сигнатуры, статическую эвристику, наблюдение за файлами и ограниченный анализ поведения процессов. Здесь важнее проследить связи частей, чем запомнить все названия.

Разбор только дополнений этапа 4 находится в [ReadMeToo_Lab4.md](ReadMeToo_Lab4.md). Короткие команды сборки и запуска — в [README.md](README.md).

Представим обычное действие: ты выбираешь файл `report.exe` и нажимаешь «Проверить». Программа должна прочитать файл, проверить его по правилам, сохранить ответ и показать объяснение. Сам `report.exe` при этом не запускается.

## Сначала — кто за что отвечает

У программы три основные части:

- **Оболочки** получают твои команды: окно или командная строка.
- **Ядро** читает файлы, загружает правила, ищет признаки и организует наблюдение.
- **Хранилище** записывает задания, результаты и основания в SQLite.

Окно вызывает ядро, но не содержит алгоритма поиска. Поэтому те же возможности доступны консольной программе и другой C++-программе, которая подключит библиотеку `Resheto::Core`.

У пары файлов с одинаковым именем обычно такое разделение: `.h` описывает доступные типы и функции, `.cpp` содержит их реализацию. Например, в `scanner.h` видно, как вызвать проверку, а в `scanner.cpp` — что она делает.

## Какие данные передаются между частями

Основные типы находятся в `src/core/model.h`:

| Тип | Что означает | Пример |
| --- | --- | --- |
| `Request` | Параметры ручной проверки | Проверить report.exe, использовать эти сигнатуры и эвристику, записать историю сюда |
| `Signature` | Одно сигнатурное правило | SHA-256 известного файла или последовательность байтов |
| `Snapshot` | Загруженный набор сигнатур с поисковым индексом | Версия базы, записи и подготовленные средства поиска |
| `Result` | Ответ по одному объекту | Совпадение, подозрение, отсутствие совпадения либо невозможность проверки |
| `Job` | Состояние всего задания | Идентификатор, время, счётчики, итог и ошибка |

Связь такая:

```text
Request задаёт работу
    → загружаются наборы правил
    → для файлов получаются Result
    → Job объединяет результаты одного запуска
```

Один каталог может дать сотни `Result`, а `Job` будет один. Во время наблюдения один `Job` объединяет целую сессию; в неё могут попасть и файловые, и поведенческие обнаружения.

`model.cpp` переводит `Result` и `Job` в JSON и обратно, проверяет допустимость полей, формирует названия итогов и код завершения. Это общий язык ядра, истории и оболочек.

## 1. Окно превращает нажатие в Request

`src/gui.cpp` — вход в графическое приложение: создаёт Qt-приложение, читает начальные аргументы, создаёт `MainWindow` и запускает обработку событий окна.

В `src/gui/mainwindow.cpp` функция `MainWindow::start()` собирает параметры из полей:

```text
path          — файл или каталог
signaturePath — база сигнатур
heuristicPath — JSON эвристики, если она включена
storagePath   — история результатов
recursive     — заходить ли в подкаталоги
```

Полученный `Request` передаётся в `controller_.submit(r)`. На этом окно поручило работу ядру. Оно продолжает обрабатывать кнопки и перерисовку.

## 2. Controller запускает проверку в фоне

Класс `Controller` находится в `src/core/controller.h/.cpp`.

`submit()` принимает запрос. Рабочий поток внутри `loop()` забирает его и вызывает `runJob()`. Через `progress()` окно получает текущую сводку `Job`; `cancel()` выставляет общий признак отмены.

Здесь не проверяются ни байты, ни признаки PE. Задача контроллера — организовать выполнение вне потока окна. Допускаются одно активное и одно ожидающее задание.

## 3. runJob организует весь запуск

В `src/core/scanner.cpp` две основные функции:

- `runJob()` отвечает за задание целиком;
- `scanFile()` проверяет один файл.

`runJob()` создаёт `Job`, открывает `Store`, загружает правила и определяет, передан файл или каталог. Для обычных файлов вызывает `scanFile()`, сохраняет ответы и обновляет счётчики. В конце записывает состояние завершения.

Если выбран каталог, обход тоже происходит здесь. Ссылки и специальные файлы не читаются. Ошибка одного объекта отражается в результате, а другие ветви продолжают проверяться. Для каталогов разрешена глубина 0–256, где корень — 0.

Так `runJob()` связывает загрузчик правил, файловый анализатор и хранилище. Само окно не обходит каталоги.

## 4. Правила на диске становятся набором в памяти

В `src/core/signatures.cpp` функция `loadSignatures()` загружает сигнатуры. Она разрешает путь через `current.json`, если передан указатель на версию, проверяет контрольную сумму, устройство SQLite и записи. Затем создаёт `Snapshot` с индексом `SearchIndex`.

У одной `Signature` есть имя, идентификатор, версия, тип, значение, маска, возможное смещение и ограничения размера файла.

Пример контрольного PATTERN: «найти байты ABC, затем любой один байт, затем DEF». В `value` записаны байты, а в `mask` отмечено, какие позиции сравнивать и какие пропускать. Если задан `offset`, последовательность должна находиться именно на этой позиции.

Включённую эвристику отдельно загружает `loadHeuristicRules()` из `src/core/heuristic.cpp`. Она возвращает `HeuristicRules`: версию, порог и список правил. Это другой набор, он не дописывается в сигнатурную SQLite.

**Снимок правил** здесь означает: загрузили определённую версию в память и используем её до конца задания. Обновление базы на диске не меняет условия посреди проверки. Это не копия проверяемого файла и не замороженная файловая система.

## 5. scanFile читает файл через ReadFile

Внутри `scanFile()` создаётся `ReadFile file(path)`. Его реализация находится в `src/core/file_access.cpp`.

`ReadFile` открывает объект только для чтения и предоставляет:

- `read()` — следующий блок данных;
- `readAt()` — ограниченное чтение с нужной позиции для разбора заголовков;
- `size()` и `identity()` — исходный размер и идентичность объекта;
- `unchanged()` — проверку, не обнаружено ли изменение или подмена.

Различия Windows и Linux скрыты внутри этого класса. Анализатору не нужно выбирать системную функцию открытия файла.

По умолчанию чтение идёт блоками по 64 КиБ. Одни и те же данные используются для расчёта SHA-256 и поиска PATTERN. Между блоками сохраняется нужный хвост, поэтому последовательность на границе блоков не теряется.

Полностью загружать большой файл в оперативную память не требуется. После чтения проверяются размер и идентичность: замеченное изменение не становится успешным ответом. Этот контроль не гарантирует обнаружение любой возможной конкурентной записи.

## 6. Как соотносятся HASH и PATTERN

Это два независимых способа сигнатурного поиска, а не выбор по расширению файла.

**HASH:** Qt вычисляет SHA-256 всего прочитанного содержимого. `SearchIndex::digest()` из `src/core/search.cpp` ищет полученное значение в таблице хешей. Так узнаётся точное совпадение содержимого с известной записью. Обычно изменение хотя бы одного байта меняет SHA-256, и прежний HASH уже не совпадает.

**PATTERN:** `SearchIndex::patterns()` ищет внутри данных заданные байты. Общий автомат Ахо–Корасик находит опорные фрагменты сразу многих шаблонов; затем проверяются весь шаблон, маска, размер и смещение. Для фиксированной позиции выполняется проверка в этой позиции.

Сейчас выбирается **одно сигнатурное обнаружение на файл**. Если PATTERN несколько, берётся совпадение с наименьшей позицией, затем с наименьшим id. Если PATTERN нет, выбирается подходящий HASH по id. Поэтому вычисление хеша идёт вместе с чтением, а окончательный выбор HASH делается после него.

Даже после найденного PATTERN файл дочитывается: поздняя ошибка или изменение должны попасть в итог. Функция `findPattern()` в том же `scanner.cpp` осталась как простой отдельный поиск; основной маршрут использует `SearchIndex`.

Рабочая база сейчас содержит **11 632 HASH и 0 PATTERN**. Сам механизм PATTERN работает и проверяется отдельной контрольной базой. Это не означает наличие поставки реальных байтовых правил известных угроз.

## 7. Если сигнатуры не совпали — включается эвристика

При включённой эвристике `scanFile()` вызывает `executableFeatures()` из `src/core/executable.cpp`. Она разбирает заголовки PE32+ или ELF64 little-endian x86-64 через тот же открытый `ReadFile` и возвращает `ExecutableFeatures`.

В этом ответе — формат, извлечённые признаки и сведения о полноте разбора. Ни Windows-, ни Linux-файл не исполняются: программа читает их устройство как данные.

Затем `evaluateHeuristics()` из `src/core/heuristic.cpp` применяет `HeuristicRules` и получает `HeuristicDecision`: найденные правила, баллы, порог, объяснение и итог.

В поставляемом `data/heuristic_rules.json` три правила:

| Признак | Баллы | Объяснение |
| --- | --- | --- |
| Область одновременно доступна для записи и исполнения | 60 | Такое сочетание заслуживает внимания |
| Ненулевая точка входа вне исполняемой области | 60 | Заявленное начало выполнения не попадает в ожидаемую область |
| Расширение не соответствует формату | 20 | Например, внутри файл PE, а называется `.txt` |

Порог — 60. Поэтому одно переименование не даёт подозрение, а первое или второе правило — даёт. Баллы не являются процентом вероятности заражения. В результате сохраняется весь список сработавших эвристических правил, хотя основное поле правила представляет одно из них.

Если сигнатурное совпадение уже найдено, этот этап не требуется. Если база сигнатур недоступна, доступная эвристика может продолжить работу, но отсутствие части анализа явно отражается в полноте и причине.

## 8. Result сохраняется раньше, чем показывается в окне

Ответ `scanFile()` возвращается в `runJob()`. Тот подготавливает обновлённые счётчики `Job` и вызывает `Store::append()`.

В `src/core/database.cpp` два уровня:

- `Database` открывает SQLite, выполняет SQL и управляет транзакциями;
- `Store` предоставляет операции программы: `start()`, `append()`, `finish()`, `latest()`, `query()` и запись/чтение наблюдений.

Результат, связанное обнаружение и счётчики сохраняются одной транзакцией. После успешной записи обновляется прогресс. Поэтому уведомление в окне относится к уже сохранённому обнаружению.

Важно различать три вида файлов:

| Файл | Для чего нужен |
| --- | --- |
| `signatures.db` | Правила узнавания известных угроз |
| `heuristic_rules.json`, `behavior_rules.json` | Отдельные правила признаков и поведения |
| `results.db` или другой выбранный файл истории | Что проверяли, что наблюдали и что получилось |

Имена файлов истории могут различаться: путь задаёт пользователь или оболочка. Скрипт `start.ps1` по умолчанию использует `build/manual/results.db`.

История содержит задания, результаты, обнаружения и события. Новый `Result` может ссылаться на наблюдение через `eventId`. Новая версия формата сохраняет чтение прежней истории; существующая SQLite при записи обновляется до схемы 3.

## 9. Как окно получает строки и объяснения

`MainWindow::tick()` периодически получает сводку от контроллера или монитора. Для строк таблицы `readPage()` обращается к `Store::query()` через асинхронное чтение.

`ResultQuery` описывает фильтр, подстроку пути, порядок и страницу. `ResultPage` возвращает строки и общее число подходящих результатов. Фильтрация и сортировка выполняются в хранилище **до** ограничения страницы в 200 строк.

Поэтому обнаружение после двух тысяч обычных строк можно найти фильтром «Совпадения», не листая всё вручную. `showDetails()` показывает основание, полноту, версию и технические сведения выбранной строки. Сам SQL остаётся внутри `Store`.

При запуске окна и смене пути истории читается последнее задание. Выбор любого старого задания отдельным списком пока не сделан. Ошибка чтения истории сохраняется на экране и останавливает активную работу, а не исчезает за следующим сообщением прогресса.

## 10. Что меняется при наблюдении за каталогом

Допустим, вместо «Начать» ты нажал «Наблюдать каталог». `MainWindow::startMonitor()` создаёт `MonitorRequest` и передаёт его в `MonitorRuntime::start()` из `src/core/monitor.cpp`.

Теперь программа ждёт новых событий. Это не первоначальная проверка всех старых файлов каталога; для неё есть ручной режим.

```text
ОС сообщает о создании или изменении файла
    → FileMonitor возвращает FileEvent
    → MonitorRuntime объединяет повторные события и ставит работу в очередь
    → рабочий поток вызывает прежний scanFile()
    → Store сохраняет событие и связанный Result
    → окно показывает обновление
```

`FileMonitor` из `src/core/file_monitor.cpp` знает системный механизм уведомлений: Windows использует `ReadDirectoryChangesW`, Linux — `inotify`. Он сообщает факт изменения, но сам не решает, опасен ли файл.

В `MonitorRuntime` есть поток получения событий и поток обработки с SQLite. По умолчанию очередь ограничена 64 работами, повторы одного пути объединяются с ожиданием 200 мс. При ошибке чтения разрешены ещё три попытки через 500 мс. Потеря событий или отказ компонента показываются явно.

Таким образом, новый файл проверяется тем же анализатором, что и выбранный вручную. Для автоматического режима не создан отдельный способ распознавания.

## 11. Как анализируются процессы

В этой ветке проверяется последовательность наблюдаемых событий. Чтение структуры исполняемого файла и наблюдение за запущенным процессом — разные задачи.

`processSnapshot()` из `src/core/process.cpp` получает доступные `ProcessInfo`: PID, PPID, время старта и путь образа. `ProcessTracker::update()` сравнивает списки и возвращает `ProcessEvent`.

PID может быть выдан повторно, поэтому идентичность включает **PID и время старта**. Первый список задаёт исходную картину. Исчезновение из доступного списка не доказывает, что процесс завершился: доступность тоже меняется.

`MonitorRuntime` передаёт подходящие события новых дочерних процессов в `BehaviorAnalyzer::observe()` из `src/core/behavior.cpp`. Применяемое правило ограничивается каталогом исполняемых файлов родителей, заданным в `processImageDirectory`; пустое поле использует наблюдаемый каталог.

Текущий `data/behavior_rules.json` задаёт один сценарий: у одного родителя наблюдены не менее трёх разных дочерних процессов за пять секунд. Анализатор возвращает `BehaviorCandidate` с правилом, родителем и событиями-основаниями.

Runtime формирует поведенческий `Result`, сохраняет его через `Store::append()` и только после успешной записи вызывает `acknowledge()`. Это подтверждение предотвращает повторную выдачу того же основания.

Это не автоматический анализ содержимого всех запущенных программ. Текущий процессный адаптер не наблюдает запись процессов в файлы, действия с реестром, сетью или памятью. Быстро завершившийся между опросами процесс может остаться незамеченным.

## Что означают итог и полнота

`outcome` отвечает, что получилось: `signature_match`, `heuristic_match`, `behavioral_match`, `no_match` или `not_checked`. `completeness` отдельно говорит о полноте выбранной проверки: `full`, `partial`, `none`.

Например, эвристическое подозрение с недоступной сигнатурной базой может иметь `partial` и сохранённое основание. Это не обычное «всё проверено». У положительного поведенческого результата `full` относится к подтверждённому сценарию, а не ко всем действиям процесса и всей ОС.

Отмена или ошибка не становятся ответом «угроз нет». Для консольных программ приоритет такой: **ошибка 2 → отмена 3 → обнаружение 1 → отсутствие обнаружений 0**. Отсутствие совпадения само по себе не доказывает безопасность.

## Многопоточность

При ручной проверке основные роли — поток окна и рабочий поток `Controller`. При наблюдении работают поток окна и два рабочих потока `MonitorRuntime`: сбор событий и их обработка. Рабочий поток контроллера при этом остаётся без задания.

Кроме них возможны кратковременные асинхронные задачи проверки базы и чтения истории. Поэтому утверждать, что во всей программе всегда ровно два потока, неправильно. Ручной режим и наблюдение в одном окне запускаются по очереди.

## Какие библиотеки используются

| Средство | Где применяется |
| --- | --- |
| C++20 и стандартная библиотека | Типы, владение ресурсами, потоки, синхронизация, файловый обход |
| Qt Core | Строки, JSON, время, аргументы CLI, SHA-256 через `QCryptographicHash`, средства подготовки |
| Qt Sql и драйвер QSQLITE | Доступ к SQLite внутри `database.cpp`, загрузка и подготовка баз |
| Qt Widgets | Графическое окно в `src/gui/` и `src/gui.cpp` |
| Qt Test | Автотесты в `tests/`, не нужен пользователю библиотеки |
| Системные API Windows/Linux | Открытие файлов, уведомления каталогов, сведения о процессах |
| Windows PSAPI | Получение сведений о памяти в инструменте измерений `benchmark.cpp` |

SQLite — локальные файлы данных; отдельный сервер базы не запускается. CMake собирает компоненты и связывает зависимости. PowerShell объединяет команды запуска и показа. Вспомогательная Python-среда в `.tools` относится к инструментам разработки; само ядро написано на C++.

| Группа файлов `.h/.cpp` | Их связь с остальными |
| --- | --- |
| `model` | Общие данные, которыми пользуются все остальные части |
| `controller`, `scanner` | Фоновое ручное задание и порядок проверки файла/каталога |
| `signatures`, `search` | Загружают сигнатуры и сопоставляют их с данными от scanner |
| `file_access` | Даёт scanner и executable доступ к одному открытому файлу |
| `executable`, `heuristic` | Извлекают признаки и применяют отдельные статические правила |
| `file_monitor`, `process` | Получают реальные факты от ОС |
| `behavior`, `monitor` | Сопоставляют события и организуют автоматическую обработку |
| `database` | Сохраняет и выдаёт результаты обоих режимов |
| `import` | Готовит и выбирает новые версии сигнатурной базы до сканирования |
| `api.h` | Собирает публичные заголовки для внешнего подключения |

В `src/gui/` находятся `mainwindow.h/.cpp`: поля, кнопки, таблицы и вызовы ядра. Остальные файлы непосредственно в `src/` создают отдельные программы:

| Файл | Как использует ядро |
| --- | --- |
| `gui.cpp` | Запускает графическую оболочку |
| `cli.cpp` | Собирает Request из аргументов, выполняет проверку или читает последнее задание |
| `monitor_cli.cpp` | Управляет MonitorRuntime из терминала |
| `prepare.cpp` | Готовит безопасные контрольные HASH/PATTERN и файлы |
| `prepare_lab4.cpp`, `fixtures.h` | Готовят собственные PE/ELF-примеры и наборы правил для этапа 4 |
| `import_main.cpp` | Даёт консольные команды для функций import |
| `benchmark.cpp` | Запускает отдельные измерения поиска и ресурсов |

В `data/` находятся исходные JSON-наборы: контрольные сигнатуры, эвристика и поведение. Подготовленные безопасные файлы создаются отдельно, обычно в `build/`. Они не являются реальными вредоносными образцами.

В `distribution/source/` сохранены внешний список SHA-256, лицензия и происхождение. В `distribution/working/` находится рабочая поставка: `current.json` выбирает каталог в `versions/`, где лежат `signatures.db`, контрольная сумма, manifest и источник версии.

`importSnapshot()` из `import.cpp` принимает внешний локальный список, проверяет записи и готовит новый каталог версии. `activateVersion()` переключает выбор; `resolveSignaturePath()` находит выбранную базу. До публикации новая версия проверяется штатным загрузчиком; при сбое прежняя выбранная версия остаётся. Источник текущих 11 632 HASH — Romain MARCOUX / malicious-hash, лицензия MIT.

В `tests/` описаны проверки поведения программы. `core_tests.cpp` проверяет чтение, поиск и обход; `audit_tests.cpp` — строгие форматы и граничные случаи; `completion_tests.cpp` — индекс, рабочую базу, импорт и запросы истории. `lab4_tests.cpp` проверяет новую статику и форматы, `monitor_tests.cpp` — живые мониторы и поведение. `integration.cpp` запускает CLI, `gui_tests.cpp` управляет окном, `powershell_scripts.ps1` проверяет скрипты. `helpers/safe_process.cpp` — собственный помощник, который ждёт и запускает только своих детей для контролируемых проверок.

В `scripts/` команды объединяются в сценарии. `start.ps1` запускает окно; `demo.ps1` показывает сигнатуры; `demo-results.ps1` — поиск обнаружения среди большого числа строк; `lab4-demo.ps1` — новые анализаторы и наблюдение. `fetch-signatures.ps1` отдельно получает метаданные, `measure.ps1` выполняет измерения, `common.ps1` содержит общие функции. Сканер и обычная сборка ничего не скачивают.

В `examples/consumer/` отдельная программа подключает сигнатурное ядро. В `examples/lab4_consumer/` внешний потребитель также вызывает эвристику, наблюдение и чтение новых результатов. Это непосредственные C++-вызовы `Resheto::Core`, а не запуск CLI вместо подключения. Заголовок — `<core/api.h>`; при отключённых GUI/тестах библиотеке не нужны Widgets и Qt Test.

В `docs/` находятся описание реализации, подключение, источник базы, проверки, измерения и исходные проектные документы. Сканер не читает эти тексты при работе. `CMakeLists.txt` в корне описывает сборку, `CMakePresets.json` — готовые конфигурации; `PROJECT_CONTEXT.md` и `AGENTS.md` фиксируют контекст и правила разработки.

`build/` хранит созданные сборки, отчёты и данные запусков. В `build/windows/Release/` находятся готовые Windows-программы, в `build/manual/` — данные стандартного ручного запуска. Внутренние `CMakeFiles`, `.qt`, `_autogen`, `.dir`, `Testing` обслуживают сборку и тесты.

`.tools/` содержит локальные SDK и инструменты: заголовки, библиотеки, DLL, плагины Qt и вспомогательные средства. `.git/` хранит историю изменений, `.gitignore` задаёт, какие создаваемые и локальные файлы не включать в неё.

## Поддержка Linux

На Linux компилируется тот же C++-проект и используется то же ядро. Не нужно запускать Windows-программу через Wine. В файловом адаптере выбираются Linux-вызовы открытия и чтения, для наблюдения — `inotify`, для процессов — `/proc`; Windows использует свои API.

Разбор PE/ELF, сигнатуры, JSON-правила и SQLite остаются общими. Формат файла не обязан совпадать с ОС анализатора: PE можно читать как данные на Linux, ELF — на Windows.

Текущая сборка и живые сценарии проверены на Windows. Linux-ветви написаны, но здесь не собирались и не запускались. Служба, IPC, сетевой анализ и карантин пока не реализованы. Сейчас наблюдение существует только пока работает запущенное приложение.

## Запуск

После сборки из корня проекта:

```powershell
.\scripts\start.ps1 -Control
.\scripts\start.ps1 -Lab4
```

Первая команда открывает безопасный показ HASH/PATTERN. Вторая — PE/ELF с эвристикой и правилами поведения. В окне нажми «Начать», выбери строку и посмотри основание. Для автоматического показа создания/изменения файлов и помощника с детьми:

```powershell
.\scripts\lab4-demo.ps1 -Output build/show-lab4-new -OpenGui
```

Выходной каталог должен быть новым. Сценарий оставит отчёты и историю; проверяемые PE/ELF не исполняются, запускается только собственный безопасный помощник.

## Вкратце

Представь проверяющего с тремя инструкциями. В первой — отпечатки известных файлов и характерные фрагменты. Во второй — признаки подозрительного устройства файла. В третьей — последовательности наблюдаемых действий, на которые стоит обратить внимание.

Ты приносишь файл. Проверяющий читает его, сверяется с первыми двумя инструкциями и записывает ответ с причиной в журнал. Если включить дежурство у папки, новые и изменённые файлы будут приноситься на ту же проверку автоматически. Другой наблюдатель сообщает о появлении процессов, а правило поведения сопоставляет эти сообщения.

Окно — место, где ты даёшь поручение и читаешь журнал. Ядро — тот, кто выполняет проверку. Базы и JSON — инструкции. История SQLite — журнал. Любое подозрение сопровождается основанием; ни отсутствие записи в инструкции, ни отсутствие замеченного события не дают гарантии безопасности.
