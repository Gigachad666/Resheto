# Лаб 5

На предыдущих этапах «Решето» проверяло файлы и наблюдало за событиями в каталогах и процессах. Теперь оно также видит сетевые пакеты и может заметить характерную последовательность соединений. Например, если один узел за короткое время обращается к множеству портов другого узла, программа покажет, какие попытки она увидела и какое правило сработало.

Сеть, ручная проверка и наблюдение запускаются отдельно. Можно включить захват, проверить файл и открыть результат вчерашнего задания в одном окне.

## Пакет, поток и обнаружение на одном примере

Представим, что программа с локального порта `53000` обращается к серверу на порту `8080`. По сети проходят отдельные **пакеты**. В заголовках видны адрес отправителя, адрес получателя, порты и протокол. Для TCP там также есть признаки начала и других этапов соединения.

Ответ сервера идёт в обратном направлении, с `8080` на `53000`. Анализатор кладёт оба направления в один **поток**. В строке потока будут две конечные точки, время первого и последнего пакета и отдельные счётчики для каждого направления. Если та же программа обращается к `8081`, образуется другой поток.

**Обнаружение** появляется, когда наблюдения удовлетворяют правилу. Если программа обратилась к двадцати разным портам одного сервера за десять секунд, в таблице будет несколько потоков, а правило может дать одну запись с основанием «20 различных TCP-портов за 10 секунд». В подробностях можно увидеть, какие события набрали этот порог. Для решения важна последовательность пакетов и время между ними.

## Реализация захвата

Во вкладке «Сеть» выбираем источник «Сетевой интерфейс», обновляем список и выбираем интерфейс. После нажатия «Начать захват» `NetworkPanel::start()` передаёт настройки в `NetworkSession`. Тот запускает отдельный процесс `resheto-network-worker`. В нём `worker.cpp` вызывает общий цикл `analyzeNetwork()` из `runner.cpp`, который открывает интерфейс через класс `Capture`.

В `capture.cpp` происходит собственно чтение из сети. На Windows `Capture` загружает библиотеку установленного Npcap из системного каталога. На Linux код обращается к системной libpcap. Вызовы одинаковые на обеих платформах. `pcap_findalldevs()` перечисляет интерфейсы, `pcap_create()` и `pcap_activate()` открывают выбранный, а `pcap_next_ex()` читает очередной пакет. Захват пассивный, обычная доставка трафика продолжается.

`captureFilter()` собирает фильтр из выбранной области. Если указать TCP-порт `8080`, в анализ попадут TCP-пакеты с этим портом и в сторону сервера, и от него. При пустом поле берётся доступный IPv4/IPv6-трафик выбранного интерфейса. `Capture::poll()` возвращает `CapturedPacket` с байтами, временем, исходной длиной и типом канального заголовка. С этим объектом дальше работает общий анализатор. Без автоостановки захват продолжается до команды «Остановить».

## Принцип анализа PCAP

PCAP — это запись сетевого трафика. У файла есть общий заголовок, а затем идут записи вида «время, длина, байты пакета». `PcapReader` из `pcap.cpp` проверяет заголовок classic PCAP 2.4, узнаёт формат времени и канальный тип, затем читает по одной записи. Например, файл может содержать кадры Ethernet, а может начинаться сразу с IP. На выходе получается тот же `CapturedPacket`, что и при живом захвате. В Windows для этого маршрута Npcap не нужен.

1. `runner.cpp` отдаёт пакет в `NetworkAnalyzer::observe()`. Там вызывается `parsePacket()` из `packet.cpp`. Разборщик определяет, где начинается IPv4 или IPv6, проверяет длины и извлекает адреса. Затем читает TCP или UDP, в том числе порты и флаги TCP. Для обычного DNS на UDP-порту 53 он может извлечь имя и код ответа. Обрезанные и неподдерживаемые данные попадают в счётчики и диагностику.
2. `analyzer.cpp` находит поток по протоколу и паре конечных точек. Для пакета `53000 → 8080` увеличивается счётчик одного направления, для ответа `8080 → 53000` — другого. У записи потока обновляются время и объём трафика.
3. Из разобранных пакетов анализатор берёт события для правил. Например, TCP-пакет с флагом `SYN` без `ACK` означает начальную попытку подключения. Анализатор смотрит, сколько разных портов набралось в нужном временном окне. При достижении порога он возвращает обнаружение с основанием.

В PCAP интервалы считаются по записанным отметкам времени. Если между двумя пакетами в записи прошла секунда, правило видит секунду, даже когда программа прочитала оба почти мгновенно. Через вкладку «Сеть» и CLI файл анализирует отдельный сетевой процесс. Из другого C++-приложения можно вызвать `scanNetworkPcap()` напрямую через `Resheto::Network`.

## Связи между новыми файлами

```text
Запуск из окна
NetworkPanel → NetworkSession → worker.cpp → runner.cpp

Путь пакета внутри общего цикла
capture.cpp или pcap.cpp → разбор в packet.cpp → правила в analyzer.cpp

Сохранение результатов
worker.cpp → NetworkSession → NetworkStore → SQLite

Чтение истории
NetworkPanel → NetworkStore → страница из SQLite
```

Старый `mainwindow.cpp` добавляет сетевую вкладку и передаёт ей путь к общей истории. Ручной проверкой и файловым наблюдением он управляет отдельно. Например, «Остановить» на вкладке сети отправляет команду только в `NetworkSession`.

Модуль `Resheto::Network` использует из прежнего `Resheto::Core` работу с файлами и SQLite. `PcapReader` открывает запись через общий `ReadFile`, а `NetworkStore` работает поверх `Database` и использует тот же файл истории, что и файловый `Store`. У сети отдельные таблицы, а в файловой проверке остаются прежние сигнатуры и правила. [file_access.cpp](src/core/file_access.cpp) · [database.cpp](src/core/database.cpp)

Если прослеживать один пакет в коде, удобная цепочка — `NetworkPanel::start()` → `analyzeNetwork()` → `NetworkAnalyzer::observe()` → `parsePacket()`.

## Правила

Для каждого задания загружается фиксированная версия набора правил. Изменения файла применятся к следующему запуску. [network_rules.json](data/network_rules.json)

| Правило | Что нужно увидеть |
| --- | --- |
| `tcp-port-sweep` | Начальные TCP-попытки к 20 разным портам одного узла за 10 секунд |
| `periodic-tcp-attempts` | Шесть попыток к одному адресу и порту за 60 секунд. Средний интервал от 1 до 10 секунд, отклонение каждого интервала от среднего до 10% |
| `dns-nxdomain-burst` | У одного клиента за 30 секунд появились ответы «имя не существует» для 20 разных имён. Анализируется обычный незашифрованный DNS на UDP-порту 53 |

У повторной отправки одного TCP-запроса и новой попытки разные роли. Анализатор подавляет дубликаты начальных TCP-пакетов. После срабатывания действует короткий период подавления для соответствующего узла или пары узлов, чтобы одна серия событий не заполняла историю одинаковыми сообщениями.

Срабатывание означает, что трафик совпал с условиями правила. Законная программа тоже может обращаться ко многим портам, поэтому в результате важны конкретные адреса, время и наблюдения, на которых основан вывод.

## Как результат попадает в историю и на экран

`NetworkSession` работает в процессе приложения и управляет сетевым процессом. `worker.cpp` запускает общий цикл из `runner.cpp`. Результаты приходят по локальному каналу группами. Контроллер записывает их через `NetworkStore` и подтверждает получение после записи. Сетевой процесс получает источник и правила, а путь к SQLite остаётся у контроллера.

В общей истории у сетевых заданий свои таблицы потоков, обнаружений и диагностики. У прежних заданий остаются свои записи. При повторном чтении выбранного сетевого задания хранилище сверяет связи обнаружений с потоками и итоговые счётчики.

`NetworkPanel` показывает прогресс и уведомления отдельно от ручной проверки. В представлении «Трафик» можно посмотреть все потоки или только потоки с обнаружениями. В «Обнаружениях» каждая строка показывает отдельное срабатывание. Можно выбрать строку, открыть «Подробности» и скопировать основание. Поиск охватывает всё выбранное задание до разбиения на страницы. Если открыт старый результат, новое срабатывание не меняет этот выбор. Для перехода есть «К запущенному заданию» или «Показать последний результат». Причины неполноты и счётчики можно открыть в боковой «Диагностике».

Здесь важно различать **процесс ОС** и **поток выполнения**. Окно и контроллер работают в одном процессе, при этом контроллер пишет историю в своём рабочем потоке. Захват и анализ выполняются в другом процессе ОС. У прежней проверки файлов и наблюдения остаются свои рабочие потоки и команды остановки.

## Запуск

Из корня проекта откройте проверенную Windows-сборку с отдельной историей показа.

```powershell
.\scripts\start.ps1 -Bin build/lab5-defaults-20261110/Release -Directory build/network-show-lab5
```

При обычной сборке в `build/windows/Release` параметр `-Bin` можно опустить. [Команды сборки](README.md#сборка-и-тесты)

- **Живой показ.** На вкладке «Сеть» выберите «Локальный показ» и пройдите шаги «1. Подготовить порты» → «2. Начать захват» → «3. Отправить трафик». Помощник работает на собственных портах `127.0.0.1`. Сначала отправьте «Два обычных соединения», затем в отдельном задании — «Двадцать разных портов». Во втором задании откройте «Обнаружения». Для живого захвата на Windows нужен установленный Npcap.
- **Показ с PCAP.** В источнике «Файл PCAP» по очереди откройте `ordinary.pcap` и `control.pcap` из `build/lab5-defaults-20261110/pcap-show`. Первый даёт ноль срабатываний, второй — три. Для новой сборки такие файлы можно создать заново через `resheto-network-prepare`. [Команды подготовки](README.md#работа-в-приложении)

На Linux предусмотрена системная libpcap. Сборка и живой захват этапа 5 на Linux здесь ещё не проверены. [Сборка и права захвата](docs/integration.md#linux-и-права-захвата)

## Один абзац

«Решето» слушает, с кем компьютер обменивается данными. Оно собирает отдельные сообщения в карточки соединений и замечает повторяющиеся схемы. Например, если программа за несколько секунд постучалась в двадцать разных «дверей» одного компьютера, «Решето» покажет, куда она обращалась и почему это привлекло внимание. Для показа мы создаём такие соединения внутри своего компьютера и сразу видим объяснение в окне.
