# Реализация этапа 3

Код использует C++20, Qt Core/SQL, Qt Widgets только в GUI. В исходном каталоге до начала работы были лишь AGENTS.md, PROJECT_CONTEXT.md, TASK_LAB3.md. Существовавший код не заменялся. Системная служба, IPC и этапы 4–6 отсутствуют.

## Компоненты и поток данных

`model` содержит Request, Snapshot, Signature, Result и Job. `signatures` создаёт/проверяет базу и загружает неизменяемый `shared_ptr<const Snapshot>`. `file_access` изолирует HANDLE Windows и fd Linux с RAII. `scanner` анализирует один открытый файл и лениво обходит область. `database` владеет соединениями SQLite и сохраняет результаты короткими транзакциями. `controller` выполняет `runJob` в одном рабочем потоке; допускает одно ожидающее задание, дальнейшие запросы отклоняет. Деструктор отменяет работу и присоединяет поток.

CLI, Qt Widgets и тесты вызывают эти же компоненты. В GUI нет поиска байтов, SHA-256, обхода и SQL. GUI опрашивает прогресс через mutex раз в 150 мс; ядро публикует его не чаще 100 мс, кроме начала/конца. Снимок прогресса заменяется, сигналы не накапливаются. Чтение истории и проверка готовности базы также асинхронны; соединение создаётся и уничтожается в использующем его потоке. Читатель истории открывает SQLite **read-only**, не выполняет DDL и не инициализирует отсутствующую базу. Таблица содержит не более 200 строк за раз. CLI выдаёт результаты постранично, без накопления всего задания.

Для будущей службы достаточно вызывать `runJob(Request)` либо `Controller::submit`, передав пользовательский каталог данных и токен отмены; общий код не зависит от Widgets. FileEvent может позднее сформировать такой же Request. Сейчас источник всех запросов — `manual`, обнаружений — `signature`. Подключение IPC, прав службы и карантина этой реализацией не имитируется.

## Формат сигнатур

Канонический читаемый пример: `data/demo_signatures.json`. `resheto-prepare` генерирует `signatures.db`, `signatures.db.sha256` и собственные безопасные фикстуры в **новом** явно указанном каталоге. `--database-only` создаёт базу без фикстур. Имена/содержимое фикстур детерминированы; `expected.json` содержит ожидаемые итоги, id и смещения. Перезапись существующего каталога запрещена; при ошибке может остаться неполный выходной каталог, что явно сопровождается кодом 2. Используйте новый путь для следующей попытки.

SQLite `user_version=1`, `application_id=1381189441`:

| Таблица/поля | Значение |
| --- | --- |
| metadata(version TEXT) | Ровно одна непустая версия базы, до 256 символов |
| signatures(id TEXT PRIMARY KEY, name TEXT, kind TEXT, value TEXT, version TEXT, enabled INTEGER) | Обязательные поля; id уникален; id/name/version непусты, до 256 символов; enabled строго 0 или 1 |
| algorithm TEXT | Для HASH только `SHA-256`; для PATTERN NULL |
| mask TEXT | NULL либо строка `0`/`1` длиной в число байтов шаблона; хотя бы одна `1` |
| offset INTEGER | NULL либо фиксированное абсолютное смещение PATTERN |
| min_size / max_size INTEGER | NULL либо включительные ограничения размера всего файла |

`value` — непрерывный hex, два символа на байт, регистр несущественен; нулевые байты разрешены. HASH имеет ровно 32 байта. Пустые/неизвестные виды, неверный hex/digest, повторный id, невалидные маски, отрицательные/дробные числа, инвертированные диапазоны, переполнение `offset + length` отклоняются. В JSON `offset/min_size/max_size` задаются **десятичными строками**; это устраняет округление больших чисел в JSON. В SQLite они целые 64-битные. Отключённые записи тоже валидируются, но не участвуют в анализе.

Лимиты: до 4096 записей, PATTERN 1..65536 байт, суммарно value+mask до 16 МиБ, файл SQLite до 64 МиБ, исходный JSON до 32 МиБ. Блок чтения 4096..4194304 байт, по умолчанию 65536. Шаблон может быть длиннее блока; хранится хвост до `maxPattern−1`. Память анализа ограничена снимком и несколькими блоками/хвостами, а не размером файла. Обход хранит стек пар «итератор, фактическая глубина». Корень имеет глубину 0; разрешены каталоги 0..256 включительно (не более 257 одновременно открытых итераторов). Глубина дочернего объекта сохраняется до удаления исчерпанного родителя из стека. Каталог глубины 257 даёт `not_checked/depth_limit` с объяснением; остальные ветви продолжаются, задание получает ошибочное завершение. Ограничение длины пути ОС может наступить раньше. Отдельной неограниченной очереди найденных файлов нет.

Manifest — отдельный ASCII hex SHA-256 **всего файла SQLite**, 64 знака и перевод строки. Сумма проверяется до/после загрузки, дополнительно проверяются schema/application id и `PRAGMA quick_check`. Базы с активным `-wal` или `-journal` не принимаются; подготовка должна завершиться и закрыть соединение до вычисления manifest. Не храните сумму внутри самого файла базы. Manifest контролирует целостность, **не подтверждает издателя**. При обновлении заменяйте базу и manifest между заданиями; загрузка в промежуточном состоянии законно завершится ошибкой. Каждое новое задание повторно проверяет базу, текущее использует только загруженный снимок.

## Сопоставление и изменения файлов

Расширение и имя файла на обнаружение не влияют. SHA-256 полного содержимого вычисляет QCryptographicHash. Все применимые PATTERN обрабатывают тот же блок и хвост, отдельных проходов файла для каждой сигнатуры нет. Поиск реализован в нашем модуле: первый значимый байт используется как опора, остальные сравниваются с учётом маски. Позиции перекрытия с уже обработанным концом не повторяются. Отмена проверяется между каталогами/блоками/сигнатурами, каждые 1024 позиции и каждые 1024 сравнения при длинном поиске.

На файл сохраняется **одно** детерминированное совпадение: сначала PATTERN с наименьшим абсолютным смещением, при равенстве — минимальный id; если PATTERN нет, HASH с минимальным id. Записи загружаются в порядке id. Чтение продолжается до EOF и при найденном шаблоне: необходимо выявить позднюю ошибку/изменение. Перечисление всех совпадений не обещается. Хеш всегда вычисляется, но в результате основание только выбранной сигнатуры; при HASH offset равен −1.

Файлы открываются только для чтения. Windows: CreateFile с OPEN_REPARSE_POINT, только disk/не directory/reparse; идентичность — volume serial + file index, размер и last-write time. Linux: open O_RDONLY|O_NOFOLLOW|O_CLOEXEC|O_NONBLOCK, fstat только S_ISREG; dev/inode/size/mtime/ctime. Перед итогом проверяются метаданные открытого объекта и текущая привязка пути. Ошибка, исчезновение, изменение/подмена либо незавершённая отмена дают `not_checked`, `completeness=none`, без подтверждённого Detection. Наблюдаемые изменения выявляются; атомарный снимок файловой системы не создаётся, все конкурентные записи гарантированно не обнаруживаются. Проверка последнего компонента пути не устраняет все гонки изменения родительских каталогов.

Символические ссылки и все Windows reparse points пропускаются, включая каталоги; устройства, FIFO и сокеты не читаются. Собственные текущие базы, manifest и SQLite sidecars исключаются по нормализованному пути, а существующие файлы дополнительно по filesystem::equivalent (включая hard links). Рекурсивность выключена — подкаталоги объяснимо пропускаются. Итераторы используют error_code; ошибка одного объекта/каталога не останавливает остальную область. Сетевых API в анализе нет; ручной выбор сетевого пути ОС отдельно не запрещён, поэтому для полностью локального показа выбирайте локальный каталог.

## Результаты и хранение

`Result`: jobId, путь, идентичность, size, итог (`no_match`, `signature_match`, `not_checked`), полнота (`full`/`none`), завершённые анализаторы, код/причина, признак пропуска, id/имя/версия сигнатуры, основание, абсолютное смещение, время UTC с `Z`, версия базы. `full` относится к выбранному сигнатурному маршруту; не обещает проверки будущими механизмами. `partial` не используется для изображения успешной незавершённой проверки.

`Job`: UUID, manual, путь, версия базы, начало/конец, running/completed/failed/cancelled, число результатов, проверенных файлов, совпадений, ошибок, пропусков, последняя обнаруженная сигнатура/путь и явная ошибка задания. `results` включает пропуски и отменённый текущий файл; `checked` — только полностью проверенные файлы. Ещё не посещённые файлы после отмены не перечисляются. После аварийного прерывания сохранённое `running` при чтении показывается как незавершённое, не как успешное. Ошибки имеют приоритет exit code 2, затем отмена 3, обнаружение 1, отсутствие совпадений 0.

`model.cpp` строго проверяет десериализацию: все сериализуемые поля обязательны и имеют заявленные JSON-типы. Целые читаются только из десятичных строк с проверкой преобразования и диапазона qint64; счётчики неотрицательны, size/offset допускают −1. Проверяются время ISO 8601 с часовым поясом, состояния, источник и счётчики без переполнения (`matches≤checked`, `checked+skipped+errors≤results`). Остаток не запрещён для running/failed/cancelled: он может представлять отменённый незавершённый объект. У успешно завершённого задания нет ошибок/остатка и есть время завершения/версия базы. Пустая версия допустима при ошибке готовности до результатов; failed без времени завершения допустим для представления прерванного задания с явной причиной. Неизвестный размер не запрещён у not_checked.

Только no_match/signature_match допускают full; для них нужны известный размер, идентичность, версия базы и завершённый сигнатурный маршрут, без ошибки/пропуска. У not_checked — none и обязательная причина/код. Совпадение требует id/имени/версии сигнатуры и основания; смещение PATTERN меньше размера файла. У остальных итогов нет сведений о подтверждённом обнаружении. Это проверка структурной и логической согласованности, не криптографическая аутентификация истории.

`resheto.db`: `user_version=1`, `application_id=1381189442`; чужие базы не инициализируются. Схема находится в `database.cpp`:

| Таблица | Хранение |
| --- | --- |
| jobs | UUID PK, started, JSON всех полей задания |
| results | row_id PK, FK job_id, JSON всех полей результата; индекс (job_id,row_id) |
| detections | UUID PK, FK job_id/result_id, source, time, signature_id/version, basis; объект/имя через результат |
| events | time с часовым поясом, type, source, object, code, FK job_id |

В одной короткой транзакции: результат, при совпадении Detection/событие, обновление счётчиков задания. Начало и конец задания — отдельные транзакции/события. Счётчики в памяти публикуются только после успешного commit. Содержимое файлов в журнал не записывается. Сбой SQLite останавливает задание с явной ошибкой; уже подтверждённые строки остаются. Если нельзя записать даже завершение, ошибка возвращается оболочке, а при следующем чтении сохранённый running виден как незавершённый. Резервного журнала ОС и миграции будущих версий схемы пока нет.

`Store::latest` читает в одной read-only транзакции Job и поток его Result, проверяет id/started против столбцов jobs, принадлежность/версию каждого результата, точное совпадение всех счётчиков и последнего обнаружения. Память не растёт с числом строк, время проверки — O(числа результатов задания). `Store::page` также строго проверяет JSON и принадлежность строки заданию; курсор страницы меняется только после успешной проверки всей страницы. Повреждение даёт явную ошибку чтения и код 2 в CLI. Формат/версия схемы остались прежними. Проверка сводки не сравнивает отдельные записи таблиц Detection/events и не восстанавливает повреждённые данные автоматически.

CLI использует `QCommandLineParser::parse`, а не завершающий процесс `process`. Ошибка разбора попадает в общий обработчик и возвращает код 2; при запросе `--json` выводится type=error, даже если неизвестная опция встретилась раньше. Корректный `--help` возвращает 0 до открытия хранилища.

GUI хранит первую ошибку истории отдельно от прогресса и показывает постоянный текст причины. При активном сканировании выставляется признак остановки из-за ошибки чтения, запрашивается отмена, автоматические повторы чтения прекращаются. Сводка показывает эту причину и фактическое состояние ядра; обычное «Отменено» не скрывает причину. Само ядро сохраняет состояние отмены — UI-ошибка чтения не меняет уже подтверждённые записи. Ручной запрос истории/страницы может повторить чтение; новое сканирование очищает сообщение. SQL и алгоритмы анализа остаются вне GUI. Управляемый тест удерживает реальный рабочий поток promise-барьером и завершает ошибочное чтение непосредственно перед `tick`, затем проверяет сообщение после остановки и его очистку при новом запуске.

## Ограничения

Поиск линейно перебирает позиции для каждой применимой сигнатуры и может быть медленным при длинных почти совпадающих шаблонах; лимиты и отмена это ограничивают, показателей производительности не заявляем. Архивы не распаковываются, альтернативные потоки NTFS и память процессов не перечисляются. Синхронный системный вызов чтения/обхода не прерывается токеном в середине: отмена наступает после его возврата; задержка на зависшем устройстве ОС возможна. Проверки Linux и ручной показ в отдельном графическом сеансе отмечены отдельно в verification.md. В дальнейшем нужны настоящие испытания на Ubuntu/Windows 10, интеграция службы и отдельное управление доверенным происхождением сигнатур.
