# Реализация файлового модуля Решето

Основа этапа 3 сохранена: ядро, сигнатурные модели, хранилище, контроллер, импорт, индексы и публичное подключение. Этап 4 дополнен 01.11.2026: ручная проверка и наблюдение работают одновременно. Служба, IPC, сеть и карантин остаются отложенными. Рабочая HASH-поставка и контрольные/синтетические данные разделены.

## Этап 4: добавленные компоненты

`executable` извлекает три структурных признака PE32+/ELF64 little-endian x86-64: существующая W+X область, ненулевая точка входа вне исполняемой области, несоответствие расширения формату. PE entry сравнивается как RVA, ELF entry — как виртуальный адрес. Нулевой entry не считается аномалией. Проверены границы/переполнения; заголовки читаются через `ReadFile::readAt` на том же объекте, до 64 КиБ за вызов, с сохранением последовательной позиции. После извлечения снова проверяется идентичность файла. Неподдерживаемый формат и повреждённая структура различаются.

`heuristic` загружает отдельный JSON до 1 МиБ, до 128 правил/1024 узлов условий/глубины 16. all/any/not используют три значения: true/false/unknown; not(unknown) остаётся unknown. Сумма весов сравнивается с порогом либо применяется critical. Готовый набор `2026.11.01-1` в `data/heuristic_rules.json` содержит два правила с весами60/60 при пороге60. Одновременное разрешение записи и исполнения одной непустой области допускает изменение исполняемых байтов; ненулевая точка входа вне исполняемой области противоречит ожидаемому расположению кода. В данном ограниченном наборе каждого признака достаточно для отметки подозрения; это не доказательство вредоносности и не вероятность. Прежнее расширение20 удалено из активного набора: при пороге60 оно практически не влияло на решение. Сам признак `extension_mismatch` по-прежнему извлекается, доступен пользовательским JSON и регрессиям. `Request::heuristicPath` явно включает расширенный маршрут; без него прежний вызов и JSON v1 сохраняются. После сигнатурного совпадения эвристика не требуется; при отказе сигнатур доступная эвристика работает с partial/причиной. Неприменимая эвристика при выполненных сигнатурах не превращает обычный файл в ошибку; при единственном неприменимом механизме объект остаётся not_checked.

`file_monitor` получает ReadDirectoryChangesW (overlapped) либо inotify. Проверяется цепочка путей от выбранного корня; ссылки не обходятся. Windows отменяет и дожидается завершения I/O перед освобождением буфера. Linux добавляет watches существующих/новых подкаталогов, снимает перемещённые, ограничивает дерево 4096 каталогами и глубиной256. Нулевая длина Windows-буфера/IN_Q_OVERFLOW и гонка установки нового поддерева отражаются как потеря полноты. Полное устранение конкурентных гонок каталогов не заявляется.

`process` получает Toolhelp/GetProcessTimes/QueryFullProcessImageName либо procfs. PID+start_time — идентичность; PPID подтверждается доступной родительской идентичностью и временем старта. Windows start_time — FILETIME, Linux — тики от загрузки ОС; это не время UTC. Первый снимок задаёт базовую линию; события означают первое наблюдение, не точное время рождения. Ограничение — 4096 доступных процессов и8192 ранее виденных lifetimes. Временно исчезнувший ключ не становится повторным child_start; переполнение сбрасывает состояние с отметкой потери.

`behavior` сопоставляет ограниченное окно наблюдённых событий с `data/behavior_rules.json`: три разных дочерних lifetime одного родителя за5с. Ключ включает процесс/правило/основания; подавление подтверждается после commit. Окно/ключи ограничены1024, правила —16, входные события и монотонный порядок валидируются. Реестр, файловые записи, сеть и память из снимков не выводятся. full у положительного сценария означает полноту проверки конкретных оснований; общий охват остаётся lifecycle_polling.

`monitor` предоставляет `MonitorRuntime::start/cancel/wait/status/processes`. Два потока получают факты и последовательно анализируют/пишут SQLite. Снимки правил загружаются один раз на сессию. Очередь64, debounce200мс, опрос процессов250мс; параметры ограничены. Повторы чтения — до трёх через500мс с прерыванием ожидания. Собственные базы/sidecars/правила исключены. Повреждение одного набора отключает только зависимую функцию; причина сохраняется. Нет доступных анализаторов — failed. Обычная остановка — cancelled/3; ошибка/потеря/отключённый запрошенный компонент дают итоговый код2.

Эти два потока принадлежат наблюдению. При одновременной ручной проверке Controller использует свой один рабочий поток, Qt Widgets — главный поток; чтение страниц/проверка базы выполняются краткими асинхронными операциями. Общий диспетчер будущей службы на этом этапе не создаётся.

Новые Result/Job имеют явный JSON schema_version=2; отдельная строгая ветка v1 сохранена. Источники signature/heuristic/behavioral, outcome heuristic_match/behavioral_match, full/partial/none, версии/правила/основания и event_id различаются. Для процесса size=-1; файловые требования не применяются к процессу. SQLite истории мигрирует1/2→3 транзакциями: detections получает rule_id/rule_version/details, events — details; старые JSON не переписываются. Read-only старой схемы не мигрирует её. `Store::latest` сверяет версии по источнику, счётчики, принадлежность и последнее обнаружение. Прерванный running показывается как failed с причиной и пустым неподтверждённым finished, сохраняя валидный round-trip.

Сессия наблюдения — один Job(source=monitor) для выбранных источников. `MonitorRequest::files` и `processes` независимы; `scanProcessImages` отдельно включает проверку файлов scoped процессов, уже живых при запуске и впервые увиденных позже. Внутри collector нужен общий системный снимок для связи с родителем, но `processes()` и журнал процессных событий ограничены выбранным каталогом программ (дочернее событие допускается по родителю из области). Образ каждого PID+start ставится в общую очередь один раз за сессию. Предел8192 идентичности останавливает постановку новых образов с явной потерей, не переиспользует старые PID как новые.

Worker вызывает обычный `scanFile` с теми же неизменяемыми сигнатурами/эвристикой. До и после чтения повторно подтверждаются PID, ID запуска и путь; завершение/подмена дают not_checked либо partial с причиной. Проверяется доступный файл по пути образа, не память и не тождество всех загруженных страниц. Связанный event `process_image` хранит процесс и область охвата `image_file_by_path`; Result сохраняет файловую identity и обычный signature/heuristic source. У behavioral Result identity — PID+start, размер−1. Эти разные объекты не смешиваются.

GUI содержит независимые панели ручной проверки и наблюдения: свои пути, рекурсия, Job/progress/cancel. Общие настройки базы/правил/истории закреплены, пока хотя бы один режим работает. Исторический выбор хранится отдельно от обоих progress и не прыгает к активному Job. В списке доступны страницы по50 заданий и возврат к новым; выбранное задание проверяется через `Store::getJob`, результаты — по вкладкам «Ручная проверка / Файловое наблюдение / Процессы». У каждой вкладки свой поиск; процессный ввод одновременно фильтрует scoped список и сохранённые результаты. Основание, ID правила, версия и фактическая ошибка показаны раздельно в подробностях; технический JSON/охват доступны ниже и в подсказках. Фильтр непроверенных включает partial. Уведомление возникает по progress после commit. Первая ошибка истории останавливает оба режима и остаётся видимой. CLI `--heuristics` opt-in; `resheto-monitor` — отдельная оболочка того же Runtime с `--no-files`, `--no-processes`, `--scan-process-images`.

Проверки этапа 4 — в [verification.md](verification.md), команды запуска и показа — в [README](../README.md). Далее описан сохранённый сигнатурный маршрут и его v1-модель; схема истории и новые исходы дополнены этим разделом.

Дополнение 26.10.2026: GUI показывает три разных назначения — объект, одна база сигнатур и история результатов. `Store::preparePath` явно создаёт родительский каталог истории при запуске из GUI; сам конструктор Store/CLI по-прежнему не создаёт несуществующий родительский каталог автоматически. Отсутствующий объект проверяется до начала задания. Сообщение ошибки открытия БД содержит русский текст, путь и отдельную техническую причину Qt/SQLite.

Скрипты запуска/показа сохраняются как UTF-8 BOM и проверяются в Windows PowerShell 5.1 и PowerShell 7. Консольные дочерние процессы читаются явно как UTF-8 через .NET Process: это предотвращает порчу русских путей/JSON при различиях кодовой страницы оболочки. Новый `scripts/start.ps1` выбирает рабочую базу либо готовит единственный контроль в build/manual/control, историю — build/manual/results.db. Сканирование/GUI не получают отдельного алгоритма для этого запуска. `scripts/measure.ps1` явно требует PowerShell 7.

## База и публикация

Схема сохранена: user_version=1, application_id=1381189441. Старые базы metadata(version) поддерживаются, показываются как «Пользовательская», источник «не указан». Новые базы содержат database_info(purpose,source): working/test/synthetic/custom задаются подготовкой; алгоритм от назначения не зависит. Импорт добавляет provenance(signature_id,source_line,source_value).

| Поле signatures | Проверяемый смысл |
| --- | --- |
| id / name / version | Непустые строки до 256 символов; уникальный id |
| kind / enabled | HASH или PATTERN; строго 0/1; disabled тоже валидируются |
| value | Непустой hex; HASH — 32 байта, algorithm=SHA-256 |
| mask | PATTERN: NULL либо 0/1 на каждый байт, хотя бы один значимый |
| offset | PATTERN: NULL либо целое 0..INT64_MAX−length |
| min_size / max_size | Неотрицательные qint64, включительный согласованный диапазон |

Лимиты: 200 000 записей, до 2 048 PATTERN, длина 1..65 536 байт, сумма value+mask до 128 МиБ, SQLite/JSON правил до 256 МиБ, внешний снимок до 128 МиБ, его строка до 4 096 байт. Проверочный профиль — 100 000 HASH + 1 000 PATTERN. Блок 4 КиБ..4 МиБ, обычно 64 КиБ. JSON offset/min_size/max_size — десятичные строки без потери точности qint64.

`signatures.db.sha256` — SHA-256 всего файла SQLite (64 hex и перевод строки). Сверяется до/после загрузки; проверяются schema/application_id, quick_check, одна непустая версия, отсутствие WAL/journal и наличие активной записи. База открывается read-only. Checksum контролирует целостность, не удостоверяет издателя.

[Импортер](signature_sources.md) принимает локальные sha256-lines и ограниченный clamav-hsb. Копирует источник, сверяет checksum, пишет SQLite в новом каталоге транзакцией. Закрытая БД с checksum и manifest проверяется штатным загрузчиком до публикации. Каталог версии выбирается одним QSaveFile current.json; previous сохраняет прежний выбор. Отказ не меняет прежний указатель/базу. После сбоя может остаться невыбранный каталог для повторного --activate. Стойкость при аппаратном отказе/отключении питания не доказана.

Request получает .db либо current.json. Каждое задание заново проверяет выбор и удерживает shared_ptr<const Snapshot> с записями и индексом. Переключение между блоками не меняет начатое задание; следующее читает новый снимок. Сигнатурный поиск не зависит от имени/расширения, test-id, каталога показа или expected.json. Эвристический признак расширения доступен отдельным пользовательским правилам этапа4; штатное решение основано на двух структурных признаках.

## Поиск и файлы

QCryptographicHash вычисляет SHA-256 по тем же блокам, что использует PATTERN. QHash отображает digest в упорядоченных по id кандидатов, затем проверяется размер. Линейного перебора 100 000 HASH на файл больше нет.

У PATTERN выбираются последние до 16 байт наиболее длинной значимой серии. Общий автомат Ахо–Корасик строится при загрузке, включает suffix/output links и не размножает выходные списки. Плотные переходы ограничены 2 048×16+1 узлами. Кандидат проверяется целиком с маской, размером и границами. Fixed offset проверяется непосредственно в окне. Частый короткий якорь может дать много кандидатов; универсальная пропускная способность не обещается. Отдельный полный проход файла для каждого правила не выполняется.

Окно — хвост maxPattern−1 и новый блок. Принимается только совпадение с впервые достигнутым концом. Поддержаны шаблоны длиннее блока. Ответ: один PATTERN с минимальным смещением, затем минимальным id BINARY; если PATTERN нет — первый применимый HASH по id. Все совпадения не перечисляются. Чтение продолжается до EOF, чтобы поздняя ошибка/изменение не превратились в подтверждение. Отмена проверяется при обходе, чтении, обходе автомата и длинных сравнениях кандидатов. Старый findPattern сохранён как простой низкоуровневый поиск; конвейер использует индекс.

Проверяемый файл открыт только для чтения. Windows: CreateFileW с OPEN_REPARSE_POINT и SHARE_READ/WRITE/DELETE, volume/file index, size/LastWriteTime до/после и повторная сверка пути. Адаптер преобразует Windows extended-length paths и обратно, без изменения настроек ОС. Linux: O_RDONLY/O_NOFOLLOW/O_NONBLOCK/O_CLOEXEC, fstat/lstat, dev/inode/size/mtime/ctime; Linux-ветвь в этой работе не проверена. Контроль выявляет наблюдаемые изменения, не создаёт атомарный снимок и не устраняет все гонки родительских каталогов.

Ссылки, reparse points и специальные файлы объяснимо пропускаются. Текущие базы/указатель/checksum/SQLite sidecars исключаются по нормализованному пути и filesystem::equivalent. Ошибка объекта не останавливает соседей. Стек содержит итератор и явную глубину: корень 0, каталоги 0..256, каталог 257 — not_checked/depth_limit с продолжением соседних ветвей. Всё дерево и весь файл в память не загружаются. Память ограничена снимком, блоками/хвостом и глубиной.

## Результаты и история

Result: jobId, путь/идентичность/size, outcome no_match/signature_match/not_checked, полнота full/none, анализаторы, code/reason/skipped, id/имя/версия сигнатуры, basis/offset, время UTC и версия базы. full означает только завершённый сигнатурный маршрут. Ошибка/изменение/отмена незавершённого файла дают not_checked без Detection. У HASH offset=−1, у PATTERN — абсолютная позиция. Отсутствие совпадения не доказывает безопасность.

Job: UUID, source=manual, путь, версия базы, время, running/completed/failed/cancelled, счётчики, последнее обнаружение и ошибка. Непосещённые после отмены объекты не перечисляются. Приоритет exitCode: ошибка 2 > отмена 3 > совпадение 1 > отсутствие совпадений 0.

Исходная схема истории user_version=1/application_id=1381189442 содержит jobs(id,started,data), results(row_id,job_id,data), detections(id,job_id,result_id,source,time,signature_id,signature_version,basis), events(time,type,source,object,code,job_id). Этап4 дополняет её до user_version=3 описанной выше миграцией; старое чтение поддерживается. Индекс results(job_id,row_id). Содержимое файлов не сохраняется. Результат, Detection/событие и счётчики фиксируются одной короткой транзакцией, память/прогресс — после commit. Сбой записи останавливает задание, ранее подтверждённые строки остаются. Чужая БД не инициализируется.

Result/Job читаются строго: обязательные поля/типы, десятичные qint64 без переполнения, состояния, сочетания outcome/completeness и сведения об обнаружении. `Store::getJob(id)` в одной read-only транзакции потоково сверяет строки, принадлежность/версии, счётчики, последнее обнаружение, соответствующие Detection и процессную связь event. `latest()` вызывает ту же проверку. По умолчанию running показывается как незавершённый failed с причиной; оболочка передаёт recoverRunning=false только для собственного известного живого задания. `jobs(offset,limit)` читает ограниченный список, выбранная запись затем проходит полную сверку. Это структурная проверка, не криптографическая аутентификация всего журнала. Соединения создаются/уничтожаются в своём потоке. Короткий process-local mutex сериализует открытие/подготовку/миграцию Store, включая первый совместный запуск в новой SQLite; работа анализаторов и обычные короткие транзакции остаются независимыми, busy timeout3с сохранён.

Store::query применяет фильтр/буквальную подстроку пути/сортировку ко всему job до LIMIT/OFFSET. Дополнительный row_id даёт стабильный порядок равных ключей, upperRow фиксирует границу представления. Используется SQLite JSON1; сохранённые JSON прежних заданий не переписываются. Широкий запрос зависит по времени от числа строк. Unicode-поиск учитывает регистр; сортировка BINARY. GUI держит до 200 строк. Во время сканирования обновляет первую страницу, переходы доступны после завершения. Изменение запроса сбрасывает страницы; поколение запроса отбрасывает устаревший асинхронный ответ. Полный путь и основание копируются из Result; у новых видов добавлены технические details.

Каждый запуск создаёт отдельную jobs-строку с новым id; прежние задания и связанные results/detections/events остаются в том же файле истории. GUI автоматически читает последнее задание при открытии и после изменения пути истории (editingFinished). Смена пути сбрасывает страницы и поколение запроса, поэтому ответ прежнего асинхронного чтения не попадает в новое представление. Пустая история очищает таблицу; её чтение не создаёт БД. Кнопка «Последнее задание» и поясняющие строки под полями/таблицей удалены. Выбор более раннего задания пока не реализован; CLI сохраняет --last.

Первая ошибка истории в GUI хранится отдельно от прогресса, не затирается обычной отменой, останавливает активное задание и автоматические повторы. Новый запуск или явная смена файла истории её очищает. CLI parse-ошибки, включая неизвестную опцию/пропущенное значение, дают 2 и type=error при --json; корректный --help — 0. Регрессии сохранены.

Архивы не распаковываются, ADS не перечисляются. Сигнатурный маршрут работает с файлами; процессное наблюдение добавлено отдельным компонентом этапа4. Системный вызов ОС не прерывается токеном в середине, зависшее устройство может задержать отмену. Рабочий HASH-список не оценивает полноту и ложные срабатывания; реальные образцы не сканировались. Проверки этапа3 и его измерения — в [verification.md](verification.md) и [performance.md](performance.md).
