# Испытания Решета

Прогон 21 ноября 2026 года на Windows 11 x64 (26200), Ryzen 7 8845HS, Qt 6.8.3 и MSVC 2022, сборка Release. Служба запускалась из терминала. Для испытаний использовались новые файлы, отдельная история SQLite и собственный трафик loopback.

## Результаты

Недоступная история дала диагностику в Windows Application. После принудительной остановки сохранённые результаты и карантин доступны, новая проверка записана. Отдельно проверена сохранность записи при последующем отказе SQLite и восстановление копии из прерванной операции. |

Нагрузочный сценарий управлял `resheto-service` через тот же локальный канал, который использует GUI. Тест `cli` проверял отдельную консольную утилиту. Тесты `gui` и `network-gui` открывали окна через Qt Test в режиме `offscreen`.

При проверке состава для Git проект заново собран из отдельной копии файлов поставки. После исправления кодировки скрипта замеров эта копия прошла CTest 12 из 12 за 139,46 с. Опубликованный скрипт из той же копии выполнил контрольную выборку и один нагрузочный прогон.

Отдельно прошли **пять сценариев с обычными окнами Windows** (`-platform windows`), включая подтверждение завершения собственного тестового процесса. В живом прогоне зарегистрировано 180 пакетов без потерь по отчёту Npcap. Уведомление появилось через 798 мс после команды отправки тестового трафика. Непрерывный захват остановлен через 31 с, остановка заняла 334 мс.

Дополнительные проверки ПМИ выполнены на Windows Release. Цикл обхода каталогов проверен через Windows junction. Обычные символические ссылки Qt Test пропустил из-за отсутствия права на их создание. После принудительной остановки только тестовой службы прежняя история открылась, карантинный файл восстановился с прежним SHA-256 и новая проверка сохранилась за 280 мс. Сценарий использовал отдельную историю и безопасный файл.

## Нагрузка

В каждом из трёх прогонов одновременно проверялся файл 128 МиБ с рабочей HASH-базой и статическими правилами, разбирался PCAP на 100 000 пакетов и работало файловое наблюдение. После запуска заданий в наблюдаемый каталог записывались 20 файлов. Во всех прогонах получены 2 075 потоков, 3 сетевых обнаружения и 20 из 20 файловых результатов со счётчиком потерь 0.

| Метрика | Прогон 1 | Прогон 2 | Прогон 3 |
| --- | ---: | ---: | ---: |
| Проверка файла, МиБ/с | 91,8 | 108,9 | 77,2 |
| Разбор PCAP, пакетов/с | 4 156 | 4 289 | 4 214 |
| Обработка всех файлов после последней записи, мс | 843 | 668 | 599 |
| Пиковый рабочий набор службы, МиБ | 38,7 | 38,8 | 39,0 |
| Наблюдавшийся пик рабочего набора сетевого процесса, МиБ | 13,4 | 13,5 | 13,5 |
| Процессорное время службы, с | 20,55 | 20,19 | 20,58 |
| Наблюдавшееся процессорное время сетевого процесса, с | 3,00 | 2,00 | 3,00 |

За 60,8 с простоя с файловым и процессным наблюдением в пустом тестовом каталоге служба использовала до 26,4 МиБ рабочего набора и 2,73 с процессорного времени. Проверка образов процессов была выключена. Время под нагрузкой включает локальный обмен, запись в SQLite и ожидание статуса задания. Память и CPU сетевого процесса считывались во время его работы, поэтому полный пик и итоговое CPU могут быть выше. Показатели относятся к конкретному ПК и контролируемому набору входов.

### Где тратится время при разборе PCAP

На той же Windows Release повторили обработку того же PCAP напрямую через `analyzeNetwork`. В двух парах прогонов чередовали два способа приёма результатов. В первом считали потоки и обнаружения в памяти, во втором дополнительно сохраняли каждую порцию в новую SQLite-историю. В обоих случаях разобрано 100 000 пакетов, получено 2 075 потоков и 3 обнаружения. [Цикл анализа](../src/network/runner.cpp)

Обработка в памяти заняла 0,58–0,74 с. Обработка с историей заняла 22,30–22,52 с, из которых 21,17–21,46 с прошли внутри `NetworkStore::append` (около 95%). В этом месте выполняются проверки согласованности, чтение предыдущего состояния и запись обновлений потоков. За прогон обработано 99 981 обновление в 1 001 порции. Замер проведён без GUI и IPC, время финальной проверки истории (67–72 мс) измерялось отдельно. Результат указывает на сохранение промежуточного состояния потоков как основное узкое место именно этого профиля. [Сохранение сетевой истории](../src/network/store.cpp)

### Повтор в Windows

Соберите Release и добавьте Qt в `PATH`, как в [README](../README.md#сборка-и-тесты). Выполните из корня проекта в PowerShell 7.2+. Скрипт сам создаёт безвредные данные в новом каталоге и сохраняет измерения в `summary.json`.

```powershell
ctest --test-dir build/windows -C Release --output-on-failure
$out = 'build/measure-service-' + [guid]::NewGuid().ToString('N').Substring(0,8)
.\scripts\measure-service.ps1 -Output $out -Bin build/windows/Release -Repetitions 3 -IdleSeconds 60
```

Для повтора с обычными окнами и установленным Npcap:

```powershell
Push-Location build/windows
try {
    & './Release/resheto-gui-tests.exe' -platform windows scanWithLocalServiceAndReopenHistory serviceProcessActionAsksAndHonorsConfirmation serviceWindowKeepsMonitoringAndOpensModuleNotifications
    & './Release/resheto-network-gui-tests.exe' -platform windows liveOwnLoopback liveUntilStoppedOnOwnPort
} finally {
    Pop-Location
}
```

Для ручной проверки в окне используйте [показ реагирования](integration.md#показ-реагирования) и [живой сетевой показ](../README.md#работа-в-приложении).

### Сопоставимый нагрузочный замер на Linux

Используйте ту же Release-сборку с сетью и службой. Для запуска скрипта нужен `pwsh` 7.2 или новее. Трафик берётся из синтетического PCAP, поэтому замер выполняется без root и прав живого захвата. [Установка PowerShell на Ubuntu](https://learn.microsoft.com/powershell/scripting/install/install-ubuntu)

```bash
out=$(mktemp -d "$PWD/build/measure-service.XXXXXX") &&
pwsh -NoLogo -NoProfile -File ./scripts/measure-service.ps1 \
  -Output "$out/run" -Bin build/release -Repetitions 3 -IdleSeconds 60 &&
printf '%s\n' "$out/run/summary.json"
```

`summary.json` содержит результаты трёх прогонов, минуту простоя, CPU, версию ОС и SHA-256 входных файлов и рабочей базы. Сначала сравните `profile_hashes` и `working_db_sha256` с прогоном Windows. Затем сравните медианы `file_mib_s`, `pcap_packets_s`, потребление памяти и CPU. Проверьте, что в каждом прогоне получено 20 файловых результатов и `monitor_lost` равен 0. На разном оборудовании это сравнение двух конфигураций целиком.

### Ручная проверка в GUI

Для живого показа подготовьте безопасные файлы и запустите службу в первом Bash. Оставьте его открытым после `READY`.

```bash
bin="$PWD/build/release"
demo=$(mktemp -d "$PWD/build/resheto-live.XXXXXX")
endpoint="resheto-$(basename "$demo")"
"$bin/resheto-prepare" --source data/demo_signatures.json --output "$demo/control"
"$bin/resheto-network-prepare" --output "$demo/network" --rules data/network_rules.json
mkdir "$demo/watched" "$demo/processes"
cp "$bin/resheto-safe-helper" "$demo/processes/"
printf 'bin=%q\ndemo=%q\nendpoint=%q\n' "$bin" "$demo" "$endpoint"
"$bin/resheto-service" --endpoint "$endpoint" --db "$demo/control/signatures.db" \
  --heuristics data/heuristic_rules.json --network-rules data/network_rules.json \
  --storage "$demo/history.db"
```

Во втором Bash из корня клона вставьте три строки `bin=`, `demo=` и `endpoint=`, выведенные первым терминалом. Запустите GUI:

```bash
"$bin/resheto" --service "$endpoint" --path "$demo/control/fixtures/exact.bin" \
  --watch-path "$demo/watched" --process-scope "$demo/processes" \
  --behavior "$PWD/data/behavior_rules.json" &
```

1. Нажмите «Проверить». В «Уведомлениях» выберите обнаружение `exact.bin` и нажмите «К результату». Отправьте файл в карантин и восстановите. Оба действия видны в «Журнале».
2. Нажмите «Начать наблюдение» и дождитесь готовности. В Bash скопируйте `cp "$demo/control/fixtures/masked.bin" "$demo/watched/"`. Откройте новое уведомление о файловом событии.
3. В том же Bash запустите `"$demo/processes/resheto-safe-helper" --children 3 --delay-ms 1000 --hold-ms 10000 &`. В «Процессах» проверьте обнаружение родителя, PID и основание. При желании завершите этого помощника через GUI, пока он жив и прошло не менее пяти секунд с запуска.
4. Во вкладке «Сеть» откройте `$demo/network/control.pcap` через источник «Файл PCAP». В «Обнаружениях» ожидаются три строки. Для живого захвата выберите «Локальный показ», подготовьте порты, запустите захват и отправьте «Двадцать разных портов». Если захват недоступен, проверьте [права сетевого процесса](integration.md#linux-и-права-захвата). PCAP и CTest работают без этих прав.
5. Остановите задания через GUI и завершите службу через `Ctrl+C` в первом терминале. Тестовая история останется в `$demo/history.db`.
