# АС «Решето»: краткий контекст реализации

## Назначение и этапы

«Решето» — локальная система антивирусного контроля для Windows и GNU/Linux. Окончательная система проверяет файлы, наблюдает файловую и процессную активность, анализирует сетевой трафик, сохраняет результаты и предоставляет подтверждаемые операции карантина. Проверяемое содержимое не отправляется во внешние системы.

| Этап | Результат | Сейчас |
| --- | --- | --- |
| 3 | Сигнатурный анализ; ручное сканирование файлов и каталогов | Реализовать полностью в пределах `TASK_LAB3.md` |
| 4 | Статическая эвристика исполняемых файлов, наблюдение за процессами, поведенческие правила, события создания/изменения файлов | Оставить возможность подключения |
| 5 | Захват трафика, разбор пакетов, учёт потоков, правила обнаружения | Не реализовывать |
| 6 | Объединение модулей, подтверждаемое реагирование и карантин, комплексные испытания | Не реализовывать |

## Принятые решения окончательной архитектуры

- C++20; Qt 6 Widgets для GUI; SQLite для локальных данных; JSON UTF-8 для правил и IPC. CMake используется как средство воспроизводимой сборки реализации.
- Целевые платформы: x86-64, Windows 10/11, Ubuntu 22.04 LTS. Поддержку других LTS подтверждают отдельными испытаниями.
- GUI и фоновая служба — два процесса. GUI работает с правами пользователя. Служба выполняет анализ независимо от подключения GUI и использует права, необходимые включённым функциям.
- Внутри службы: диспетчер заданий, мониторы, независимые анализаторы, уведомления, карантин, хранилище. Общий пул — два рабочих потока; очереди ограничены.
- Локальный IPC: именованный канал Windows / AF_UNIX Linux, кадры с длиной и JSON. Доступ ограничен средствами ОС; разрыв связи не отменяет задание.
- Платформенные адаптеры отвечают за запуск службы, IPC, файловый доступ/наблюдение, процессы и захват трафика. Анализаторы используют общие форматы.
- Отдельная SQLite-база `signatures.db` хранит сигнатуры. `resheto.db` хранит результаты, обнаружения и журнал; правила следующих этапов поставляются отдельно.

**Граница текущего этапа:** самостоятельный файловый модуль с минимальным GUI и тестовым запуском. Здесь GUI может вызывать фасад модуля в своём процессе через асинхронный контроллер. Это промежуточный способ запуска, а не замена окончательной архитектуры GUI + служба. Системная служба, привилегированный IPC и постоянное наблюдение появятся при дальнейшей интеграции. Для текущего показа административные права не требуются.

## Контракты, существенные для этапа 3

Названия ниже логические; точное объявление C++ выбирается по существующему коду. Сохрани смысл и не размножай одинаковые модели.

| Сущность | Минимальное содержание |
| --- | --- |
| FileScanRequest | Идентификатор задания, путь, режим обхода, источник `manual`, токен отмены |
| Signature | Идентификатор, имя, вид HASH/PATTERN, значение, версия, enabled; ограничения поиска |
| ScanResult | Задание, путь и идентичность объекта, итог, полнота, выполненные анализаторы, совпадения/основания, ошибки, версия базы |
| Detection | Идентификатор, источник `signature`, объект, время, идентификатор/имя/версия сигнатуры, основание |
| ScanJob | Состояние задания, время, счётчики, ссылки на результаты; отменённое/ошибочное завершение отличается от успешного |
| LogEntry | Время с часовым поясом, тип события, источник, объект, результат/код ошибки, requestId/jobId |

Итог объекта и полнота проверки — разные поля. В текущем этапе нужны как минимум `no_match`, `signature_match`, `not_checked`. Полнота `full` относится только к выбранному сигнатурному маршруту, а не ко всем будущим механизмам системы. Ошибка чтения, исчезновение/изменение объекта или отмена незавершённого анализа не дают `no_match`. Значение `partial` предусмотрено общей моделью для последующего сочетания анализаторов, но не должно изображать успешно завершённую сигнатурную проверку.

## Сигнатуры

- **HASH:** точное сравнение SHA-256 всего содержимого; совпадение имени, размера или расширения недостаточно.
- **PATTERN:** поиск последовательности байтов в содержимом; поддерживаются маска и необязательное фиксированное смещение от начала файла.
- Побайтовая маска: `0` — байт игнорируется, `1` — требуется равенство. Длина маски совпадает с длиной шаблона; отсутствие маски означает точное сравнение всех байтов.
- `min_size` / `max_size` ограничивают размер файла, к которому применима сигнатура. Отсутствие фиксированного `offset` означает поиск по содержимому.
- Обязательны id, name, kind, value, version/enabled; для HASH указывается алгоритм SHA-256. Представление BLOB/hex выбери однозначно, документируй и валидируй.
- При загрузке проверяются версия схемы, поля, идентификаторы, корректность записей и контрольная сумма. Для файловой контрольной суммы используй отдельный manifest/sidecar: сумма всего файла не хранится внутри того же файла. Это контроль целостности, не подтверждение доверенного издателя.
- Задание удерживает неизменяемый снимок валидной базы до завершения. Текущему этапу не нужен отдельный сервис обновлений и автоматическое скачивание базы.

## Файловый конвейер

1. Обойти выбранную область, получить обычный файл. По умолчанию не следовать символическим ссылкам и каталогам Windows с reparse point; не читать устройства, сокеты и каналы.
2. Открыть файл для чтения, сохранить идентификатор открытого объекта, размер и время изменения. Чтение и сопоставление выполняются по этому открытому объекту.
3. Применить доступные сигнатуры. Читать блоками; при поиске шаблонов учитывать перекрытие `максимальная_длина_шаблона − 1`, абсолютные позиции и отмену между блоками.
4. Перед окончательным результатом проверить метаданные открытого объекта и, когда возможно, привязку пути к нему. Изменившийся/подменённый объект вернуть как не проверенный с причиной.
5. Сохранить результат и при совпадении Detection, обновить прогресс. Ошибка одного файла не останавливает обход остальных.

Проверка идентификатора и метаданных выявляет наблюдаемые изменения, но не создаёт атомарный снимок файловой системы и не гарантирует обнаружение всякой конкурентной записи. Не заявляй обратного. Отличия Windows/Linux изолируются в небольшом компоненте файлового доступа.

## Хранение и дальнейшее развитие

Начало/завершение задания, результаты, обнаружения и ошибки сохраняются в `resheto.db`. Ошибки записи видимы пользователю. Соединения SQLite не используются небезопасно из нескольких потоков; запись организована короткими транзакциями. Рабочие данные текущего этапа хранятся в доступном пользователю каталоге приложения либо явно заданном каталоге, не в исходниках. Защищённые каталоги службы `%ProgramData%\Resheto` и `/var/lib/resheto` относятся к последующей интеграции.

Этап 4 добавит эвристику после отсутствия сигнатурного совпадения и вызов этого же конвейера от FileEvent. Поведенческий и сетевой анализ формируют общий Detection; они не должны менять алгоритм сигнатурного поиска. Операции с файлами выполняет отдельная подсистема карантина по подтверждённой команде, не сигнатурный модуль.
