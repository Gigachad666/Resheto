# Этап 6. Как «Решето» стало одним комплексом

К пятому этапу у «Решета» уже были сигнатурная проверка файлов, эвристика, наблюдение за файлами и процессами и сетевой анализ. На шестом этапе их объединили вокруг фонового процесса `resheto-service`. Он запускает задания, хранит их историю и выполняет действия по обнаружениям. Окно показывает результаты и отправляет команды. Его можно закрыть во время проверки и позже подключиться снова.

## Что добавилось

- **Отдельная служба.** Ручная проверка, наблюдение и сеть имеют свои задания и команды остановки. Служба принимает команды от окна той же учётной записи. Для сети она по-прежнему запускает отдельный `resheto-network-worker`.
- **Общие уведомления и журнал.** Из уведомления можно перейти к конкретному файлу, процессу или сетевому потоку. В журнале остаются события задания, ошибки и действия пользователя. Результаты можно открыть после перезапуска службы. Активное наблюдение и захват после перезапуска включаются заново.
- **Файловый карантин.** Пользователь выбирает обнаружение и подтверждает действие. Служба сверяет, что по сохранённому пути всё ещё лежит тот же файл с тем же SHA-256. Упаковка хранится отдельно от истории SQLite. Восстановление требует свободного пути. При конфликте можно указать другой путь.
- **Завершение процесса.** Из обнаружения можно запросить остановку конкретного живого процесса. Служба проверяет PID, время запуска, образ, владельца и возраст экземпляра от пяти секунд. Пользователь подтверждает действие. Результат записывается в журнал.
- **Запуск средствами ОС.** В Windows предусмотрен режим `--scm`, на Linux — запуск через пользовательский `systemd`. Для обычного показа достаточно запустить службу из терминала. [Системный запуск](docs/integration.md#запуск-под-управлением-ос)

## Как это работает на одном примере

Нажимаем «Проверить» для контрольного `exact.bin`. Окно передаёт путь службе. Она запускает файловый модуль, который читает байты и находит контрольный PATTERN. Служба сохраняет обнаружение и основание в SQLite. Уведомление в окне ведёт к этой строке результатов.

Затем выбираем «В карантин…». После подтверждения служба сверяет файл с сохранённым обнаружением, проверяет созданную упаковку и убирает исходный файл с прежнего места. Появляется запись в журнале. Из карантина файл можно восстановить. Пока мы работаем с этой строкой, файловое наблюдение и сетевой анализ могут продолжать свои задания.

## Технический стек

Основной код написан на **C++20 и Qt 6**. CMake собирает ядро `Resheto::Core`, сетевую библиотеку `Resheto::Network`, службу и оконное приложение отдельными целями.

| Технология | Как используется |
| --- | --- |
| **Qt Core** | `QCoreApplication` запускает цикл событий службы, `QTimer` обрабатывает периодические действия, `QFile` работает с файлами, `QCryptographicHash` считает SHA-256. |
| **Qt Network** | `QLocalServer` и `QLocalSocket` дают IPC через именованный канал Windows или Unix-сокет Linux. Сообщение состоит из четырёх байтов длины и JSON. Это позволяет прочитать сообщение целиком, даже если канал отдаёт его по частям. |
| **Qt SQL и SQLite** | Драйвер `QSQLITE` открывает локальную базу. История заданий, уведомления и состояния реакций хранятся в таблицах. |
| **Qt Widgets** | `QTableWidget` показывает строки результатов, `QMessageBox` запрашивает подтверждение действий. |
| **Готовые API ОС и захвата** | Windows SCM подключается через `Advapi32`. Для завершения проверенного экземпляра используются дескриптор процесса и `TerminateProcess` на Windows, `pidfd` на Linux. Живой захват использует Npcap или libpcap соответственно. |
| **Qt Test и инструменты проверки** | `QTemporaryDir` создаёт отдельную папку для истории и входных файлов. `QProcess` запускает собранную службу и безвредных помощников. `QCOMPARE` проверяет ожидаемые значения, `QTRY_VERIFY_WITH_TIMEOUT` ждёт результата фоновой операции. |

## Запуск в Windows

Все команды выполняются в PowerShell из корня проекта. На этой машине можно использовать готовую сборку `build/lab6-process-20261120`. Для обычного запуска окна с рабочей базой выполните:

```powershell
.\scripts\start.ps1 -Bin .\build\lab6-process-20261120\Release
```

Для показа уведомлений, карантина и журнала откройте два PowerShell. В первом подготовьте контрольные данные и запустите службу. Если `build/lab6-show` уже существует, выберите новое имя и используйте его в обоих терминалах.

```powershell
$env:PATH = "$PWD\.tools\qt\6.8.3\msvc2022_64\bin;$env:PATH"
$bin = '.\build\lab6-process-20261120\Release'
$demo = 'build/lab6-show'
& "$bin/resheto-prepare.exe" --source data/demo_signatures.json --output $demo
if ($LASTEXITCODE -ne 0) { throw 'Не удалось подготовить контрольные файлы' }
& "$bin/resheto-network-prepare.exe" --output "$demo/network" --rules data/network_rules.json
if ($LASTEXITCODE -ne 0) { throw 'Не удалось подготовить контрольный PCAP' }
New-Item -ItemType Directory -Path "$demo/watched", "$demo/processes" | Out-Null
Copy-Item -LiteralPath "$bin/resheto-safe-helper.exe" -Destination "$demo/processes/"
& "$bin/resheto-service.exe" --endpoint resheto-lab6-show --db "$demo/signatures.db" --heuristics data/heuristic_rules.json --network-rules data/network_rules.json --storage "$demo/history.db"
```

После `READY resheto-lab6-show` оставьте первый терминал открытым. Во втором запустите окно:

```powershell
$env:PATH = "$PWD\.tools\qt\6.8.3\msvc2022_64\bin;$env:PATH"
$bin = '.\build\lab6-process-20261120\Release'
$demo = 'build/lab6-show'
& "$bin/resheto.exe" --service resheto-lab6-show --path "$demo/fixtures/exact.bin" --watch-path "$demo/watched" --process-scope "$demo/processes" --behavior data/behavior_rules.json
```

1. Нажмите «Проверить». В «Уведомлениях» нажмите «К результату» на обнаружении `exact.bin`. Поместите файл в карантин с подтверждением, восстановите его и проверьте обе записи в «Журнале».
2. Нажмите «Начать наблюдение» и дождитесь готовности. В свободном PowerShell из корня проекта выполните `Copy-Item 'build/lab6-show/fixtures/masked.bin' 'build/lab6-show/watched/'`. Новое обнаружение должно связаться с заданием наблюдения.
3. Для процессного примера из того же каталога запустите `& './build/lab6-show/processes/resheto-safe-helper.exe' --children 3 --delay-ms 1000 --hold-ms 10000`. Если Qt для этого терминала ещё вне `PATH`, повторите строку настройки `PATH` из блока запуска. В «Процессах» появится обнаружение по дочерним процессам помощника. Пока родитель жив и ему не меньше пяти секунд, можно проверить ручное завершение.
4. В «Сети» откройте `build/lab6-show/network/control.pcap` через источник «Файл PCAP». Ожидаются три обнаружения. Для живого сетевого показа доступны «Локальный показ» и собственный трафик loopback, на Windows для этого нужен Npcap. [Живой сетевой показ](README.md#работа-в-приложении)
5. Остановите задания через GUI и нажмите `Ctrl+C` в первом терминале. История показа останется в `build/lab6-show/history.db`.

Если для повтора изменили имя каталога, используйте его и в ручных шагах.

## Как запускаются автоматические тесты

```powershell
$env:PATH = "$PWD\.tools\qt\6.8.3\msvc2022_64\bin;$env:PATH"
$ctest = '.\.tools\python\cmake\data\bin\ctest.exe'
$build = '.\build\lab6-process-20261120'
& $ctest --test-dir $build -C Release --output-on-failure
```

Чтобы проверить только этап 6 на уровне службы, используйте `& $ctest --test-dir $build -C Release -R '^service$' --output-on-failure`. `-N` выводит список зарегистрированных групп, а `-V` показывает вывод отдельных сценариев даже при успешном результате. Исходные команды для сборки на другом ПК есть в [README](README.md#сборка-и-тесты).

| Группы CTest | Что они проверяют |
| --- | --- |
| `service` | Независимые задания, сохранение истории после переподключения, карантин и восстановление, завершение собственного тестового процесса. |
| `gui`, `network-gui` | Управление заданиями и подтверждения в окне, навигацию по истории, доступ к обнаружениям и разделение трафика и обнаружений. |
| `core`, `completion`, `audit` | Сканирование, сигнатуры, хранение результатов и обработку ошибок, отмены и неполной проверки. |
| `lab4`, `monitor` | Эвристику PE/ELF, файловое наблюдение и поведенческий сценарий с собственными процессами. |
| `network`, `network-runtime` | Разбор PCAP, потоки, правила, остановку и обмен с сетевым процессом. |
| `cli`, `scripts-powershell51` | Консольные коды возврата, JSON, повторное чтение и запуск сценариев в Windows PowerShell, включая пути с пробелами и кириллицей. |

`12/12` — число пройденных групп CTest. В одной группе обычно несколько тестовых сценариев Qt Test. `Passed` сообщает итог группы, время рядом — её длительность. `Total Test time (real)` показывает прошедшее время всего запуска. В выводе Qt Test `PASS` и `FAIL` относятся к отдельному сценарию, `SKIP` означает пропуск, `QWARN` — предупреждение, `QINFO` — дополнительное измерение или сообщение. Например, `latency_ms` в `QINFO` показывает задержку в миллисекундах для конкретного сценария.

С установленным Npcap можно отдельно запустить проверку живого захвата на собственном loopback-трафике. Она проверяет параллельный запуск и независимую остановку заданий:

```powershell
$env:RESHETO_SERVICE_LIVE = '1'
Push-Location $build
try {
    & '.\Release\resheto-service-tests.exe' liveLoopbackAndIndependentStops
} finally {
    Pop-Location
    Remove-Item Env:RESHETO_SERVICE_LIVE
}
```

Для повтора с обычными окнами Windows используйте сценарии Qt Test из [отчёта](docs/testing.md#повтор-в-windows).

## Как измеряли нагрузку

Скрипт загружает контролируемые данные через интерфейс службы. В каждом нагрузочном прогоне одновременно проверяется файл 128 МиБ, анализируется PCAP на 100 000 пакетов и отслеживаются 20 новых файлов. Для простоя служба в отдельном прогоне около минуты наблюдает за пустой областью с файловым и процессным наблюдением. Прогон использует свою историю и сохраняет результаты в `summary.json`.

Из корня проекта в PowerShell 7.2+ после настройки `PATH`:

```powershell
$out = 'build/measure-service-' + [guid]::NewGuid().ToString('N').Substring(0,8)
.\scripts\measure-service.ps1 -Output $out -Bin .\build\lab6-process-20261120\Release -Repetitions 3 -IdleSeconds 60
```

| Поле в `summary.json` | Что означает |
| --- | --- |
| `system`, `os_description`, `cpu`, `timestamp_utc` | На какой системе и процессоре получены числа и когда запущен замер. |
| `quality` | Контрольные результаты. `positive` и `negative` — число положительных и отрицательных примеров. `expected_missed` и `unexpected_matches` — пропущенные ожидаемые и лишние срабатывания. `job_id` связывает запись с заданием в тестовой истории. |
| `profile_hashes`, `working_db_sha256` | SHA-256 файла, PCAP и рабочей базы. По ним сверяют входы между прогонами. `service_sha256` и `worker_sha256` фиксируют конкретные бинарники. |
| `profile[].startup_ms`, `file_ms`, `pcap_ms` | Время до `READY`, завершения файловой проверки и завершения разбора PCAP. Профиль учитывает локальный обмен, запись в SQLite и ожидание статуса задания. |
| `file_mib_s`, `pcap_packets_s`, `flows` | Скорость проверки файла в МиБ/с, скорость разбора PCAP в пакетах/с и число сохранённых сетевых потоков. |
| `monitor_files`, `monitor_lost`, `monitor_after_last_write_ms` | Сколько файлов обработано, сколько событий зарегистрировано как потерянные и через сколько миллисекунд после последней записи были готовы все результаты. |
| `service_peak_mib`, `worker_sample_peak_mib` | Пиковый рабочий набор службы и наблюдавшийся при опросе пик сетевого процесса. |
| `service_cpu_seconds`, `worker_sample_cpu_seconds` | Секунды процессорного времени службы и сетевого процесса. Сетевой процесс считывается во время работы, поэтому итоговое CPU может быть выше. |
| `idle` | Фактическая длительность простоя, память, CPU и потери при включённом наблюдении. |

На Windows прошли 12 из 12 групп. В сопоставимых прогонах Windows на Ryzen получил медианы 119,1 МиБ/с и 4 191 пакет/с. Manjaro в QEMU получил 81,9 МиБ/с и 2 584 пакета/с. Во всех прогонах обработаны все 20 файловых событий без потерь, хеши входов совпали. Замер сравнивает две конфигурации целиком. Живой захват и запуск под systemd на Linux проверяются отдельно. [Полные результаты и команды Linux](docs/testing.md)

## Один абзац для объяснения

«Решето» — это окно и фоновый процесс. Окно отдаёт команды, а фоновый процесс проверяет файлы, наблюдает за событиями и собирает результаты в журнал. Если находит совпадение, сразу показывает, какой файл или процесс привлёк внимание и почему. Дальше человек решает, отправлять ли файл в карантин или завершать процесс. Мы проверили каждое действие на безопасных примерах и измерили, как весь комплекс работает, когда он занят сразу несколькими делами.
